# ADR-019: Enum V2 Projection — Minimal on-chain taxonomy for formal verification

**Date**: 2026-04-14
**Status**: Active
**Author**: Sim (architect) + Opus (Gatekeeper auditor)
**Dependencies**: ADR-005 (confidence tiers), ADR-006 (claim hash), ADR-012 (deterministic bifurcation), ADR-014 (smart contract audit)
**Findings resolved**: S1-001 (`security_audit` enum rejected on-chain), S1-002 (`KeyError` on `deterministic`/`verdict`)
**Axioms invoked**: 3 (regression-cut transparency), 4 (local computation, on-chain proof)

---

## 1. Context

### 1.1 — The problem

The `epistemic_type` field crosses three layers of the system with inconsistent vocabularies:

- **Python (`attestation.py`)**: 8 types accepted by the Pydantic validator (`foundational`, `bridge`, `specialized`, `generalist`, `hybrid`, `verdict`, `deterministic`, `security_audit`).
- **Bridge (`bridge.py`)**: 6 types in `EPISTEMIC_TYPE_MAP` — `deterministic` and `verdict` missing → `KeyError` at serialization (S1-002).
- **Rust (`lib.rs`)**: `require!(epistemic_type <= 4)` — `security_audit` mapped to `5` is rejected on-chain (S1-001).

This misalignment blocks on-chain anchoring of any attestation produced by the deterministic path (ADR-012) and the audit engine (ADR-014).

### 1.2 — The Lean 4 constraint

EPP targets a formal specification layer where the invariants of the epistemic protocol are specified in Lean 4. Each on-chain enum value is a case in every formal statement. An 8-value enum (some with no formally distinct semantics) would make the specification needlessly complex and brittle to future additions.

The question is not "which types deserve to go on-chain" but "which types are formally distinguishable and verifiable".

### 1.3 — The rejected alternative

**Extending the Rust enum to 8 values** (the "ON-CHAIN for everyone" option) would have resolved S1-001 and S1-002 but committed to a permanent on-chain interface contract for types whose formal semantics are indistinguishable. `foundational` and `bridge` flow through the same ESMM pipeline, produce scores via the same multi-LLM consensus, and are subject to the same tier invariants — distinguishing them on-chain provides no verifiable property and burdens every proof with redundant cases.

---

## 2. Decision

### 2.1 — Three on-chain categories formally verifiable

The Rust enum is reduced to 3 values. The Python bridge performs a **projection** from the 8 business types to these 3 categories.

| u8 | On-chain category | Projected Python types | Common trait |
|----|-------------------|-------------------------|--------------|
| 0 | `empirical` | foundational, bridge, specialized, generalist, hybrid, verdict | Score from a multi-LLM consensus |
| 1 | `deterministic` | deterministic | External authoritative source (ADR-012) |
| 2 | `assessed` | security_audit | Assessment driven by a specialized pipeline (ADR-014) |

### 2.2 — Projection irreversible by design

The projection is a **surjective, non-injective function**. Several Python types produce the same on-chain value. Granular information is lost on-chain. This is a deliberate choice, not a limitation:

- The original Python business type stays in the `portable_json` stored in SQLite (`attestations` table, `portable_json` column).
- The `claim_hash` (ADR-006) deterministically links the on-chain record to the full off-chain record.
- Reconstructing the original Python type from an on-chain PDA is **impossible by design**. A PDA reader sees `empirical`, `deterministic`, or `assessed` — never `foundational` or `hybrid`.

### 2.3 — Dual source of truth

The projection table is maintained in two files that must remain manually synchronized:

| Source of truth | File | Role |
|-----------------|------|------|
| **Python** | `services/solana/bridge.py::EPISTEMIC_TYPE_MAP` | Python → u8 serialization |
| **Rust** | `programs/epp/src/state.rs::epistemic_type_to_u8()` | Rust documentation (helper not called by instructions — the client sends u8 directly) |

**Invariant**: for every type `t` accepted by `attestation.py`, the value `EPISTEMIC_TYPE_MAP[t]` must equal `epistemic_type_to_u8(t)`. This consistency is not checked automatically in CI (no cross-language test). It relies on developer discipline and the Gatekeeper C1 control.

**Risk**: an addition of a type in one file without updating the other passes silently. Mitigation: the Python tests (`test_epistemic_type_v2_s1_001_s1_002.py`) cover all 8 types in the map. Any addition of a type in `attestation.py` without updating `EPISTEMIC_TYPE_MAP` triggers a `KeyError` caught by these tests.

### 2.4 — Adding a future Python type

Procedure to add a new business type (e.g., `geopolitical_assessment`):

1. Add the type to `attestation.py::validate_epistemic_type::allowed`.
2. Decide its on-chain category (`empirical`, `deterministic`, or `assessed`) and add the entry to `EPISTEMIC_TYPE_MAP`.
3. Update `state.rs::epistemic_type_to_u8()` to document the new mapping.
4. **No Rust redeploy required** — the u8 value sent to the program is already in the `[0, 2]` range. The Rust program has no knowledge of Python types.
5. Add a round-trip test in `test_epistemic_type_v2_*.py`.

This is the key property of the projection: the on-chain enum is stable against the addition of Python business types.

## 3. Lean 4 invariants — enforcement status

Each on-chain category carries a formally statable invariant. The goal is to prove these invariants in Lean 4 over a specification of the Rust program (post-hackathon roadmap).

| Invariant | Target formal statement | Enforced on-chain (lib.rs) | Enforced off-chain (Python) | Lean 4 |
|-----------|------------------------|---------------------------|----------------------------|--------|
| **Empirical tier boundary** | `∀ a : Attestation, a.epistemic_type = 0 ∧ a.confidence_tier = 3 → a.consensus_score ≥ 8500 ∧ a.models_consulted ≥ 3` | ❌ No | ✅ `attestation.py` (partial — threshold checked, `models_consulted ≥ 3` checked for `verified` tier) | Roadmap |
| **Deterministic source anchor** | `∀ a : Attestation, a.epistemic_type = 1 → a.source_anchor ≠ [0u8; 32]` | ❌ No | ⚠️ Partial (`pipeline.py::crystallize` requires `source_anchor_meta` but doesn't assert non-nullity of the hash itself) | Roadmap |
| **Assessed domain rules** | To be defined in a dedicated ADR | ❌ No | ❌ No | Roadmap |
| **Regression cut isolation** (Axiom 3) | `∀ a₁ a₂ : Attestation, a₁.claim_hash = a₂.claim_hash ∧ a₁.frame_hash ≠ a₂.frame_hash → ¬comparable(a₁, a₂)` | ❌ No (the program does not compare attestations) | ✅ `compute_claim_hash()` includes the frame in the hash → distinct PDAs | Roadmap |
| **Claim hash purity** (ADR-006) | `claim_hash = SHA256(subject ‖ predicate ‖ object ‖ frame)` — no metadata | ✅ Implicit (the program receives the precomputed hash) | ✅ `compute_claim_hash()` | Roadmap |

**Main gap**: the `empirical tier boundary` and `deterministic source anchor` invariants are not enforced on-chain. The Rust program checks value bounds (`consensus_score <= 10000`, `epistemic_type <= 2`) but not inter-field relations. No issue on devnet (the Python client is the only submitter). Blocking for mainnet — a malicious submitter could submit a `deterministic` attestation with `source_anchor = [0; 32]` or an `empirical` attestation with `verified` tier and score 0.

## 6. Open questions

**Q1** — Should we enforce inter-field invariants directly in `lib.rs` (e.g., `if epistemic_type == 1 { require!(source_anchor != [0; 32]) }`) before the Lean 4 pass? Advantage: immediate protection against malicious submitters on devnet. Cost: redeploy + program complexity. **Decision deferred** — acceptable as long as the only submitter is the controlled Python pipeline.

**Q2** — Is adding the `assessed` category sufficient, or should we plan a future subdivision (e.g., `assessed_security` vs `assessed_geopolitical`)? The answer depends on the Lean 4 formalization: if invariants differ by domain, subdivision is justified. Otherwise, `assessed` stays a unitary bag.

**Q3** — The `state.rs::epistemic_type_to_u8()` helper is not called by any instruction. Should it be removed (less dead code) or kept (executable documentation)? **Current decision**: keep it, with comment `// NOTE: Helper not called by instructions — kept for documentation and cross-language coherence with bridge.py`.
