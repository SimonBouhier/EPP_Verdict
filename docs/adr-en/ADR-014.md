# ADR-014: Epistemic Smart Contract Audit Engine

**Date**: 2026-03-05
**Status**: Proposed
**Dependencies**: ADR-005 (multi-criteria tiers), ADR-006 (claim hash), ADR-010 (methodology traceability), ADR-012 (deterministic bifurcation), ADR-013 (epistemic cache)
**Axioms invoked**: 1 (model obsolescence), 3 (regression-cut transparency), 4 (local computation, on-chain proof)

---

## 1. Context

### 1.1 — The opportunity

The existing VERIFY pipeline (ASSESS → CHALLENGE → ADJUDICATE) transposes mechanically to smart contract auditing. Each claim asserts the presence or absence of a vulnerability in a portion of code. Epistemic uncertainty measures (consensus_score, vote_entropy, dissent_score, Brier scores) allow objective comparison of model performance against reference human audits.

The availability of **public ground truth** (Trail of Bits, OpenZeppelin, PeckShield, Solodit reports) makes EPP quantitatively benchmarkable for the first time. Vote entropy becomes a discovery signal: high entropy on a function = zone to investigate, exactly like a human auditor concentrates attention on unusual code.

### 1.2 — SoTA validation: alignment with Trail of Bits (March 2026)

The EPP approach is validated by the practices of Trail of Bits, the world leader in smart contract auditing:

- **`entry-point-analyzer`** (Claude Code plugin, trailofbits/skills): identifies state-changing functions, classifies them by access level (public/admin/role-restricted/contract-only), excludes view/pure/read-only. This is exactly the role of our `contract_slicer.py`. Our slicer draws inspiration from it but produces `ContractUnit`s formatted for the VERIFY pipeline instead of textual reports.

- **`building-secure-contracts`**: 11 specialized skills covering 6 blockchains + 5 guideline assistants. The 9-category maturity framework (arithmetic safety, access controls, complexity, MEV risks, etc.) is a future EPP extension axis (see §8, Q5).

- **Slither `--print entry-points`**: natively lists state-changing entry-points with their state variables. When Slither is available, our slicer can use it as a first pass instead of regex parsing, then enrich with context (imports, inheritance, modifiers).

- **Trail of Bits audit format** (cf. LooksRare audit 2022, 15 findings): Finding + Severity (High/Medium/Low/Informational — 4 levels, not 5) + Vulnerability Class (Access Controls, Timing, Undefined Behavior, Patching, Data Validation, Auditing/Logging, Configuration, Cryptography) + Response (Acknowledged/Rejected + Additional Comments). Our output format supports both the SWC taxonomy and Trail of Bits classes (see §2.2).

- **`crytic/not-so-smart-contracts`**: examples of real vulnerabilities with annotated source code, maintained by Trail of Bits. Priority reference dataset for our benchmark (code + description + vulnerable pattern + recommendation).

**What EPP adds vs the state of the art**: the Trail of Bits skills are single-model workflows (Claude Code). EPP is the only system that submits the same function to N architecturally distinct models, measures their disagreement (vote_entropy), and anchors the quantified consensus on-chain. The delta between a single-model audit and an EPP multi-model audit is measurable and constitutes the unique value proposition.

### 1.3 — The immediate technical constraint: context window

Local models (mistral ~8K, llama3.1 ~8-128K, deepseek-r1 ~64K via Ollama) cannot ingest a full multi-thousand-line contract as prompt context. Even models with theoretically large windows significantly degrade their attention quality beyond ~4K tokens of source code.

**Immediate architectural choice: per-function decomposition.** The contract is pre-split into atomic units (functions, modifiers, constructors), each submitted as an independent claim to the VERIFY pipeline.

**This choice is explicitly provisional.** The architecture MUST preserve the future possibility of submitting an entire contract via large-context APIs (GPT-4, Claude, Gemini). The slicing module is an isolated and replaceable component, not an assumption buried in the pipeline. Two branches will eventually coexist: the `function_level` branch (lightweight, compatible with small local models) and the `full_contract` branch (cloud APIs, large context). The first never disappears — it remains the universal fallback.

### 1.4 — The double path: epistemic + deterministic

Smart contract auditing naturally combines EPP's two paths:

- **Epistemic path (ESMM)**: models deliberate on semantic vulnerabilities — reentrancy, access control, business-logic flaws. This is the core value: model disagreement signals ambiguous zones.

- **Deterministic path (ADR-012)**: static-analysis tools (Slither, Mythril, Solhint) produce binary, reproducible results. They are integrated as authoritative sources via the existing `SourceAdapter` pattern.

The two paths produce distinct attestations linked by `previous_hash` (ADR-006). The deterministic path reinforces the signal without polluting the epistemic consensus.

### 2.2 — Decomposition module: `contract_slicer.py`

**Single responsibility**: receive a source file (.sol or .rs), extract auditable units, and produce a list of claims formatted for the VERIFY pipeline.

```python
@dataclass
class ContractUnit:
    """Atomic unit extracted from a smart contract."""
    unit_id: str                    # hash(contract_path + function_name)
    contract_path: str              # Path of source file
    contract_name: str              # Contract name (e.g., "TokenVault")
    unit_type: str                  # "function" | "modifier" | "constructor" | "fallback"
    unit_name: str                  # Function name (e.g., "withdraw")
    source_code: str                # Raw source code of the unit
    visibility: str                 # "public" | "external" | "internal" | "private"
    access_level: str               # "public" | "admin" | "role_restricted" | "contract_only"
                                    # (aligned with Trail of Bits entry-point-analyzer)
    modifiers: List[str]            # Modifiers applied (e.g., ["onlyOwner", "nonReentrant"])
    state_writes: List[str]         # State variables modified (static extraction)
    external_calls: List[str]       # External calls detected (static extraction)
    line_range: Tuple[int, int]     # Start-end lines in the source file
    context_imports: str            # Relevant imports and inheritance (max 500 tokens)

@dataclass
class ContractSliceResult:
    """Result of contract slicing."""
    contract_path: str
    contract_hash: str              # SHA-256 of full source file
    language: str                   # "solidity" | "rust_anchor"
    units: List[ContractUnit]
    total_lines: int
    slice_strategy: str             # "function_level_v1" — versioned (Axiom 3)
    skipped_units: List[str]        # Skipped units (e.g., pure view without state)
    slither_assisted: bool          # True if Slither entry-points was used
```

**Slicing strategy `function_level_v1`**:

1. **Parser**: two modes. Slither mode (if available): `slither <path> --print entry-points --json -` provides state-changing functions, their variables, and their visibility. Regex fallback mode: robust patterns for Solidity (function/modifier/constructor/fallback/receive), AST-lite for Rust Anchor (#[instruction]). No mandatory dependency on an external compiler.
2. **Access classification**: aligned with Trail of Bits entry-point-analyzer — `public` (no restrictive modifier), `admin` (onlyOwner/onlyAdmin), `role_restricted` (RBAC, AccessControl), `contract_only` (internal + external calls from known contracts).
3. **Enrichment**: each unit is annotated with its `state_writes` and `external_calls` (static extraction by grep on the function body). These annotations feed the ASSESS prompt.
4. **Context**: imports, inheritance, and storage declarations are added in a compact preamble (`context_imports`, capped at 500 tokens) to give models the minimum contract context.
5. **Filtering**: `pure`/`view` functions without external calls are flagged `low_priority` (audited if the token budget allows, skipped otherwise).

**Future path — `full_contract_v2`**: a second `slice_strategy` to implement when large-context APIs are available. The whole contract is passed as a single block with a structured prompt requesting a global audit. The two strategies coexist via the `slice_strategy` field in `ContractSliceResult` and `consensus_meta`. Function-level vs full-contract comparison is an explicit benchmark axis.

### 2.3 — Dual severity taxonomy

The SoTA uses two competing taxonomies:

| Taxonomy | Levels | Used by |
|:---|:---|:---|
| **Trail of Bits** | High / Medium / Low / Informational (4) | ToB, ConsenSys Diligence |
| **SWC + competitions** | Critical / High / Medium / Low / Informational (5) | Immunefi, Sherlock, Code4rena |

EPP supports both via a `severity_taxonomy` field in the frame:

```python
# In the smartcontract_audit_v1.0 frame
"severity_taxonomy": "tob_4level",  # or "swc_5level"
"severity_levels_tob": ["high", "medium", "low", "informational"],
"severity_levels_swc": ["critical", "high", "medium", "low", "informational"],
```

**Hackathon choice**: `tob_4level` by default (alignment with the reference firm). Mapping `swc_5level → tob_4level` is trivial: `critical` → `high`. Taxonomy choice is documented in `consensus_meta.audit_meta.severity_taxonomy`.

### 2.4 — Adaptation of VERIFY prompts for audit

New templates in `cycle_prompts.py` — VERIFY/AUDIT mode:

**ASSESS_AUDIT**: the model receives a `ContractUnit` and must produce:
- Classification by category: SWC Registry (SWC-107, SWC-104, etc.) AND/OR Trail of Bits vulnerability classes (Access Controls, Timing, Undefined Behavior, Data Validation, etc.)
- Verdict per potential vulnerability: `VULNERABLE` / `SAFE` / `UNCERTAIN`
- Confidence [0,1] and textual evidence with line numbers
- Severity per the active taxonomy (`tob_4level` by default)

**CHALLENGE_AUDIT**: circular rotation identical to standard VERIFY. Model[i] receives the verdict from model[(i+1)%N] and must contest or confirm it with specific code arguments (line numbers, detected patterns).

**ADJUDICATE_AUDIT**: synthesis of all verdicts. Production of a per-category score vector, plus a global security score.

**Extension of `claim_type`**: new value `"security_audit"` in the `cycle_manager.py` majority vote. Penalty factor in `CLAIM_TYPE_PENALTIES`: `"security_audit": 1.0` (no penalty — it's an empirically verifiable claim).

**ASSESS_AUDIT prompt format**:

```
<CONTRACT_CONTEXT>
// Imports and inheritance
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
contract TokenVault is ReentrancyGuard {
  mapping(address => uint256) public balances;
</CONTRACT_CONTEXT>

<FUNCTION_UNDER_AUDIT>
function withdraw(uint256 amount) external {
    require(balances[msg.sender] >= amount, "Insufficient balance");
    (bool success, ) = msg.sender.call{value: amount}("");
    require(success, "Transfer failed");
    balances[msg.sender] -= amount;
}
</FUNCTION_UNDER_AUDIT>

<UNIT_METADATA>
visibility: external | access_level: public | modifiers: none
state_writes: [balances] | external_calls: [msg.sender.call]
</UNIT_METADATA>

Assess this function for security vulnerabilities.
For EACH potential vulnerability found, respond in JSON:
{
  "vulnerabilities": [
    {
      "swc_id": "SWC-107",
      "tob_class": "Undefined Behavior",
      "title": "Reentrancy in withdraw",
      "severity": "high",
      "verdict": "VULNERABLE",
      "confidence": 0.95,
      "evidence": "Line 4: external call before state update (line 5). Classic checks-effects-interactions violation.",
      "affected_lines": [4, 5]
    }
  ],
  "overall_safety": "VULNERABLE",
  "summary": "..."
}
```

### 2.7 — Isolated audit database: `epp_audit_devnet.db`

Audit attestations are stored in `data/epp_audit_devnet.db`, never in `data/epp_devnet.db`. The two databases share the same schema (`schema.sql`) but are physically separated.

**Justification**: audit attestations must not pollute the main knowledge graph. The main pipeline's Brier scores, epistemic cache (ADR-013), and tier transitions stay isolated from audit data.

**The benchmark** uses a third ephemeral DB (`data/benchmark_audit.db`) created and destroyed per benchmark run. This DB is never persisted.

### 2.10 — Integration with ADR-013 (Cache)

The epistemic cache applies to audits in `epp_audit_devnet.db`: if the same function of the same contract (identified by `contract_hash + unit_id`) has been deliberated within the TTL, the cache returns the existing attestation. The `contract_hash` changes if the source code is modified → automatic invalidation.

For the benchmark, `use_cache=False` is mandatory (consistent with `scenario_6`).

## 5. Implementation constraints

### 5.1 — Audit module isolation

The `services/audit/` directory is an autonomous module. It imports `pipeline.run_pipeline()` and `services/sources/adapters/`, but **no existing module imports `services/audit/`**. Audit is a consumer of the pipeline, not a component of the pipeline.

Single exception: `cycle_prompts.py` receives the audit templates. This is consistent with the existing pattern (EXPLORE + VERIFY templates already coexist in this file).

### 5.2 — The slicer is replaceable

`contract_slicer.py` exposes an interface `slice_contract(path, strategy) → ContractSliceResult`. The `strategy` is a versioned parameter. The `function_level_v1` slicer is the first implemented. A future `full_contract_v2` is a drop-in replacement.

The slicer must NEVER be called from the ESMM pipeline. It is called by `audit_runner.py` which then calls the pipeline N times.

### 5.3 — Prompt formatting

The source code of a `ContractUnit` is injected into the ASSESS_AUDIT prompt between explicit tags (`<CONTRACT_CONTEXT>`, `<FUNCTION_UNDER_AUDIT>`, `<UNIT_METADATA>`). The metadata (visibility, access_level, state_writes, external_calls) is passed in a separate section so the model can use it without "inventing".

### 5.4 — The benchmark does not touch production DBs

`audit_benchmark.py` uses an ephemeral SQLite DB (`data/benchmark_audit.db`), never `data/epp_audit_devnet.db` or `data/epp_devnet.db`. Benchmark attestations do not pollute any persistent graph.

### 5.5 — `services/rwa/` → `services/sources/` migration (procedure)

This task is a **blocking prerequisite**. Formal procedure:

1. **Diagnostic**: Claude Code runs `grep -rn "services/rwa\|services.rwa\|from.*rwa" --include="*.py" .` and transmits the raw output
2. **Opus validation**: scope check, identification of risky zones (circular imports, `__init__.py`, tests)
3. **Migration script**: Claude Code produces a dedicated Python script that performs the rename (directory + all imports) atomically
4. **Supervised execution**: the script is run, results sent to Opus
5. **C1 audit**: `grep -rn "services/rwa" --include="*.py" .` must return 0 results
6. **Non-regression**: `pytest tests/ -q` — identical baseline tests (none added or removed)
7. **Documentation update**: ARCHITECTURE.md, CHANGELOG.md, config.yaml if needed

## 6. Risks

| Risk | Probability | Mitigation |
|:---|:---|:---|
| Local 7B models hallucinate non-existent vulnerabilities | High | `vote_entropy` will be high → explicit uncertainty signal. The benchmark precisely measures the false-positive rate. The deterministic path (Slither) serves as baseline. |
| Per-function decomposition loses inter-function context | High | `context_imports` (500 tokens) partially mitigates. The ADR explicitly documents this limit and the `full_contract_v2` roadmap. The benchmark will measure the gap. |
| Slither not installed on all users' machines | Medium | The Slither adapter is optional. If absent, the deterministic path is skipped and `consensus_meta.audit_meta.static_analysis_integrated = false`. The slicer uses the regex fallback mode. |
| SWC categories don't cover Rust/Anchor | Certain | Phase 1 = Solidity only. Anchor extension in Phase 2 with adapted taxonomy. |
| Source contract too large (>200 functions) | Low for MVP | Static-signal prioritization: functions with `external_calls` + `state_writes` audited first. `pure`/`view` functions last. |
| `services/rwa/` → `services/sources/` migration breaks imports | Medium | Formal procedure §5.5 with C1 audit post-migration. |

## 8. Open questions — COMMUNITY_DECISION_REQUIRED

**Q1 — Contract-level aggregation.** N functions produce N attestations. **Hackathon approach: semi-automated structured pre-indexing.** The global score is the weakest-link score (min severity × min consensus_score). The N individual attestations form a rich structured index — each function, its verdict, its entropy, its SWC/ToB category — consultable by a human auditor. The machine produces the index and signal; the human pronounces the final verdict. **Long-term vision:** when models become more mature and benchmarks have proven the reliability of automatic aggregations, the index can be "wrung out" into a single aggregated verdict. This transition will be an explicit benchmark axis (correlation index→human verdict on N audits).

**Q2 — Granular vs aggregated on-chain attestation.** Should we anchor on-chain each attestation per function, or only the aggregated contract attestation? The Solana transaction cost is linear in N. A compromise: anchor the aggregate on-chain, store details off-chain (SQLite in `epp_audit_devnet.db`) with the `previous_hash` link.

**Q3 — Audit update.** A contract audited at T is modified at T+30d. The `contract_hash` changes → attestations are invalidated. Should there be a diff-audit mechanism (audit only modified functions)? This requires a semantic diff module, not just textual.

**Q4 — Slither/ESMM interaction.** If Slither detects a vulnerability but the ESMM judges it `SAFE`, what tier should be assigned? If the ESMM detects but not Slither? **Hackathon approach:** concordance/discordance is a documented signal in `consensus_meta.audit_meta.static_analysis_concordance`, not an automatic resolution. The structured index presents both verdicts side by side. The human decides. **Long-term vision:** when sufficient correlation data has accumulated (Phase 2+ benchmark), a concordance→tier weighting model can be empirically calibrated.

**Q5 — Extension beyond security.** Auditing for gas optimization, standards compliance (ERC-20/721/1155), or code quality follows the same pattern. The Trail of Bits `code-maturity-assessor` framework (9 categories: arithmetic safety, access controls, complexity, MEV risks, etc.) is a natural blueprint. Separate frames recommended (`smartcontract_gas_v1.0`, `smartcontract_erc20_compliance_v1.0`) rather than overloading the single frame — consistent with the "one frame = one measurement domain" approach (ADR-005).
