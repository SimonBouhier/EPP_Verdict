# ADR-019 : Projection Enum V2 — Taxonomie on-chain minimale pour vérification formelle

**Date** : 2026-04-14
**Statut** : Actif
**Auteur** : Sim (architecte) + Opus (auditeur Gatekeeper)
**Dépendances** : ADR-005 (confidence tiers), ADR-006 (claim hash), ADR-012 (bifurcation déterministe), ADR-014 (audit smart contracts)
**Findings résolus** : S1-001 (enum `security_audit` rejetée on-chain), S1-002 (KeyError `deterministic`/`verdict`)
**Axiomes mobilisés** : 3 (transparence des coupures), 4 (computation locale, preuve on-chain)

---

## 1. Contexte

### 1.1 — Le problème

Le champ `epistemic_type` traverse trois couches du système avec des
vocabulaires incohérents :

- **Python (`attestation.py`)** : 8 types acceptés par le validateur Pydantic
  (`foundational`, `bridge`, `specialized`, `generalist`, `hybrid`, `verdict`,
  `deterministic`, `security_audit`).
- **Bridge (`bridge.py`)** : 6 types dans `EPISTEMIC_TYPE_MAP` — `deterministic`
  et `verdict` absents → `KeyError` à la sérialisation (S1-002).
- **Rust (`lib.rs`)** : `require!(epistemic_type <= 4)` — `security_audit`
  mappé à `5` rejeté on-chain (S1-001).

Ce désalignement bloque l'ancrage on-chain de toute attestation produite
par le chemin déterministe (ADR-012) et par le moteur d'audit (ADR-014).

### 1.2 — La contrainte Lean 4

EPP vise une couche de spécification formelle où les invariants du
protocole épistémique sont spécifiés en Lean 4. Chaque valeur de l'enum
on-chain est un cas dans chaque énoncé formel. Un enum à 8 valeurs
métier (dont certaines sans sémantique formelle distincte)
rendrait la vérification inutilement complexe et fragile face aux ajouts
futurs.

La question n'est pas "quels types méritent d'aller on-chain" mais
"quels types sont formellement distinguables et vérifiables".

### 1.3 — L'alternative rejetée

**Étendre l'enum Rust à 8 valeurs** (option "ON-CHAIN pour tout le monde")
aurait résolu S1-001 et S1-002 mais engagé un contrat d'interface on-chain
permanent pour des types dont la sémantique formelle est indistinguable.
`foundational` et `bridge` transitent par le même pipeline ESMM, produisent
des scores par le même consensus multi-LLM, et sont soumis aux mêmes
invariants de tier — les distinguer on-chain n'apporte aucune propriété
vérifiable et charge chaque preuve de cas redondants.

---

## 2. Décision

### 2.1 — Trois catégories on-chain formellement vérifiables

L'enum Rust est réduit à 3 valeurs. Le bridge Python effectue une
**projection** depuis les 8 types métier vers ces 3 catégories.

| u8 | Catégorie on-chain | Types Python projetés | Trait commun |
|----|--------------------|-----------------------|--------------|
| 0 | `empirical` | foundational, bridge, specialized, generalist, hybrid, verdict | Score issu d'un consensus multi-LLM |
| 1 | `deterministic` | deterministic | Source autoritaire externe (ADR-012) |
| 2 | `assessed` | security_audit | Évaluation dirigée par pipeline spécialisé (ADR-014) |

### 2.2 — Projection irréversible par design

La projection est une **fonction surjective, non injective**. Plusieurs
types Python produisent la même valeur on-chain. L'information granulaire
est perdue on-chain. C'est un choix délibéré, pas une limitation :

- Le type métier Python original reste dans le `portable_json` stocké en
  SQLite (table `attestations`, colonne `portable_json`).
- Le `claim_hash` (ADR-006) lie de manière déterministe l'enregistrement
  on-chain à l'enregistrement off-chain complet.
- La reconstruction du type Python original depuis un PDA on-chain est
  **impossible par design**. Un lecteur de PDA voit `empirical`,
  `deterministic` ou `assessed` — jamais `foundational` ou `hybrid`.

### 2.3 — Double source de vérité

La table de projection est maintenue dans deux fichiers qui doivent
rester synchronisés manuellement :

| Source de vérité | Fichier | Rôle |
|------------------|---------|------|
| **Python** | `services/solana/bridge.py::EPISTEMIC_TYPE_MAP` | Sérialisation Python → u8 |
| **Rust** | `programs/epp/src/state.rs::epistemic_type_to_u8()` | Documentation Rust (helper non appelé par les instructions — le client envoie u8 directement) |

**Invariant** : pour tout type `t` accepté par `attestation.py`, la valeur
`EPISTEMIC_TYPE_MAP[t]` doit être identique à `epistemic_type_to_u8(t)`.
Cette cohérence n'est pas vérifiée automatiquement en CI (pas de test
cross-langage). Elle repose sur la discipline du développeur et sur le
contrôle Gatekeeper C1.

**Risque** : un ajout de type dans un fichier sans mise à jour de l'autre
passe silencieusement. Mitigation : les tests Python
(`test_epistemic_type_v2_s1_001_s1_002.py`) couvrent les 8 types dans
le map. Tout ajout de type dans `attestation.py` sans mise à jour de
`EPISTEMIC_TYPE_MAP` provoque un `KeyError` capté par ces tests.

### 2.4 — Ajout d'un futur type Python

Procédure pour ajouter un nouveau type métier (ex. `geopolitical_assessment`) :

1. Ajouter le type dans `attestation.py::validate_epistemic_type::allowed`.
2. Décider de sa catégorie on-chain (`empirical`, `deterministic`, ou
   `assessed`) et ajouter l'entrée dans `EPISTEMIC_TYPE_MAP`.
3. Mettre à jour `state.rs::epistemic_type_to_u8()` pour documenter le
   nouveau mapping.
4. **Aucun redéploiement Rust requis** — la valeur u8 envoyée au programme
   est déjà dans la plage `[0, 2]`. Le programme Rust n'a pas connaissance
   des types Python.
5. Ajouter un test round-trip dans `test_epistemic_type_v2_*.py`.

C'est la propriété clé de la projection : l'enum on-chain est stable
face à l'ajout de types métier Python.

## 3. Invariants Lean 4 — statut d'enforcement

Chaque catégorie on-chain porte un invariant formellement énonçable.
L'objectif est de prouver ces invariants dans Lean 4 sur une spécification
du programme Rust (post-hackathon roadmap).

| Invariant | Énoncé formel cible | Enforcé on-chain (lib.rs) | Enforcé off-chain (Python) | Lean 4 |
|-----------|---------------------|--------------------------|---------------------------|--------|
| **Empirical tier boundary** | `∀ a : Attestation, a.epistemic_type = 0 ∧ a.confidence_tier = 3 → a.consensus_score ≥ 8500 ∧ a.models_consulted ≥ 3` | ❌ Non | ✅ `attestation.py` (partiel — threshold vérifié, `models_consulted ≥ 3` vérifié pour tier `verified`) | Roadmap |
| **Deterministic source anchor** | `∀ a : Attestation, a.epistemic_type = 1 → a.source_anchor ≠ [0u8; 32]` | ❌ Non | ⚠️ Partiel (`pipeline.py::crystallize` requiert `source_anchor_meta` mais n'asserte pas la non-nullité du hash lui-même) | Roadmap |
| **Assessed domain rules** | À définir par ADR dédié | ❌ Non | ❌ Non | Roadmap |
| **Regression cut isolation** (Axiome 3) | `∀ a₁ a₂ : Attestation, a₁.claim_hash = a₂.claim_hash ∧ a₁.frame_hash ≠ a₂.frame_hash → ¬comparable(a₁, a₂)` | ❌ Non (le programme ne compare pas les attestations entre elles) | ✅ `compute_claim_hash()` inclut le frame dans le hash → PDAs distincts | Roadmap |
| **Claim hash purity** (ADR-006) | `claim_hash = SHA256(subject ‖ predicate ‖ object ‖ frame)` — pas de metadata | ✅ Implicite (le programme reçoit le hash pré-calculé) | ✅ `compute_claim_hash()` | Roadmap |

**Gap principal** : les invariants `empirical tier boundary` et
`deterministic source anchor` ne sont pas enforcés on-chain. Le programme
Rust vérifie les bornes des valeurs (`consensus_score <= 10000`,
`epistemic_type <= 2`) mais pas les relations inter-champs. Aucun
problème en devnet (le client Python est le seul submitter). Bloquant
pour mainnet — un submitter malveillant pourrait soumettre une attestation
`deterministic` avec `source_anchor = [0; 32]` ou une attestation
`empirical` avec tier `verified` et score 0.

## 6. Questions ouvertes

**Q1** — Faut-il enforcer les invariants inter-champs directement dans
`lib.rs` (ex. `if epistemic_type == 1 { require!(source_anchor != [0; 32]) }`)
avant le passage Lean 4 ? Avantage : protection immédiate contre
submitters malveillants sur devnet. Coût : redéploiement + complexité
du programme. **Décision reportée** — acceptable tant que le seul
submitter est le pipeline Python contrôlé.

**Q2** — L'ajout d'une catégorie `assessed` est-il suffisant ou faut-il
prévoir une subdivision future (ex. `assessed_security` vs
`assessed_geopolitical`) ? La réponse dépend de la formalisation Lean 4 :
si les invariants sont distincts par domaine, la subdivision est justifiée.
Sinon, le type `assessed` reste un sac unique.

**Q3** — Le helper `state.rs::epistemic_type_to_u8()` n'est appelé par
aucune instruction. Faut-il le supprimer (moins de code mort) ou le
garder (documentation exécutable) ? **Décision actuelle** : garder, avec
commentaire `// NOTE: Helper not called by instructions — kept for
documentation and cross-language coherence with bridge.py`.
