# ADR-020 : Architecture Dual-Trust — Invariants formels Lean 4

**Date** : 2026-04-17
**Statut** : Actif (v1 — clôture de la première session Lean)
**Dépendances** : ADR-001 (encodage float↔u16), ADR-005 (tiers multi-critères), ADR-006 (claim hash déterministe), ADR-012 (bifurcation déterministe), ADR-017 (réseau de clusters), ADR-019 (Enum V2 on-chain)
**Axiomes mobilisés** : 3 (transparence des coupures), 4 (computation locale, preuve on-chain)

---

## 1. Contexte

### 1.1 — L'enjeu épistémique

EPP_Verdict revendique d'être un protocole de consensus AI **formellement vérifiable**. Cette revendication est ambiguë si elle n'est pas qualifiée. Le standard implicite du public technique est celui de la vérification formelle de smart contracts (Certora, K Framework, ChronosVault) : toutes les instructions du programme sont prouvées, l'absence de panic est garantie, les invariants globaux tiennent sous tous les états accessibles.

Ce standard n'est **pas** celui atteint ici, et ne peut pas l'être avec les outils disponibles en avril 2026 : la traduction automatique Rust → Lean 4 (Aeneas, hax) reste expérimentale, et Certora ne supporte pas Anchor 0.32. Sur-promettre « programme formellement vérifié » serait trompeur.

### 1.2 — Le piège de la sur-promesse

Le `LEAN4_RESEARCH_BRIEF.md` documente quatre pièges à éviter, dont le plus coûteux en crédibilité :

> **Piège n°4 — Sur-promesse académique.** Dire « formellement vérifié » alors qu'on a prouvé trois lemmes sur l'encodage u16 est trompeur. Honnêteté > impressionnant.

Le présent ADR formalise la position défendable : **le protocole épistémique abstrait** a un ensemble d'invariants formellement prouvés en Lean 4. Le lien entre ces preuves et le code runtime (Python, Rust) est documenté, vérifié par observation, mais **pas mécaniquement garanti**. Cette distinction est structurelle, pas temporaire.

### 1.3 — La découverte du 2026-04-17 qui force la rigueur

Au cours de la session du 2026-04-17, trois problèmes structurels ont été débusqués dans l'infrastructure de preuves existante :

1. Le théorème `tier_verified_implies_conditions` (INV-4) était **incomplet** — sa preuve ne compilait pas.
2. Le fichier `RedTests.lean` n'était **pas inclus** dans `lake build` par défaut, parce que `Main.lean` n'importait pas la lib `Formal`.
3. La CI Lean (`lean_action_ci.yml`) exécutait la cible par défaut, donc ne compilait ni la lib ni les red tests.

Conséquence : pendant environ cinq semaines, la documentation du projet a affirmé « trois invariants prouvés avec red tests de non-tautologie » alors que (a) un des trois invariants n'était pas effectivement prouvé et (b) les red tests n'étaient pas exercés par la CI. Ce n'était pas un mensonge — c'était un angle mort de garde-fou.

Cette découverte donne sa force à ce qui suit : les exigences de cet ADR ne sont pas théoriques. Elles répondent à un mode de défaillance observé.

## 2. Décision — Architecture Dual-Trust

### 2.1 — Deux couches de confiance complémentaires

EPP_Verdict repose sur **deux couches de confiance distinctes**, qu'il ne faut pas confondre :

| Couche | Source de confiance | Garantie | Limite |
|:---|:---|:---|:---|
| **Empirique** (runtime) | Consensus multi-LLM + sources déterministes | Convergence observable, Brier scores, signature 5D | Confiance statistique, pas mathématique. Dépend des modèles et des sources. |
| **Mathématique** (spécification) | Preuves Lean 4 sur le protocole abstrait | Invariants formellement prouvés sur un modèle | Le modèle n'est pas le code. Le lien modèle↔code est humain. |

Les deux couches **ne s'opposent pas** et **ne se substituent pas**. Elles couvrent des risques différents :

- La couche empirique gère le risque « le modèle se trompe sur le monde ».
- La couche mathématique gère le risque « le protocole se trompe sur lui-même ».

### 2.2 — Ce que prouve la couche Lean 4

La couche Lean 4 prouve que **le protocole**, défini comme une spécification mathématique, a les propriétés structurelles souhaitées. Elle ne prouve pas :

- Que SHA-256 est sûr (cryptographie, hors scope).
- Que l'implémentation Python respecte la spécification (gap sémantique, §5).
- Que l'implémentation Rust respecte la spécification (gap sémantique, §5).
- Qu'aucun bug d'implémentation n'existe en runtime.

Elle prouve que **si** le code runtime implémente fidèlement la spécification, **alors** les propriétés tiennent nécessairement.

### 2.3 — Pourquoi c'est utile malgré ces limites

1. **Documentation exécutable.** Un théorème Lean est une spécification qui ne peut pas dériver silencieusement. Si un jour quelqu'un modifie `assignTier` pour abaisser un seuil, le théorème TierBoundary échoue à la compilation. C'est un garde-fou que le commentaire en prose ne peut pas fournir.

2. **Lecture auditable.** Un auditeur externe (reviewer hackathon, académique, agent IA reprenant le repo) peut lire `Formal/` en dix minutes et connaître exactement les propriétés garanties du protocole. Sans ADR-020 et sans `Formal/`, cette compréhension demanderait une lecture complète du code Python et Rust.

3. **Préparation pour Phase 3.** Lorsque les outils Rust↔Lean matureront (Aeneas, hax, autres), le fossé pourra être comblé mécaniquement. Les preuves actuelles sont la fondation sur laquelle cette extraction future s'appuiera.

## 3. Inventaire des invariants prouvés (2026-04-17)

Onze théorèmes sont actuellement prouvés et compilés dans la lib Lean, répartis en cinq modules. Le build `lake build` par défaut compile la totalité (18 jobs).

### 3.1 — Module `Formal/Encoding.lean` — INV-1

| Théorème | Propriété prouvée |
|:---|:---|
| `score_bounded` | Tout `Score` construit a `val ≤ 10000`. |
| `zero_score_valid` | Le score 0 est valide et décodable. |
| `max_score_valid` | Le score 10000 est valide et décodable. |
| `score_roundtrip_bounded` | Tout score encodé puis décodé reste dans `[0, SCORE_SCALE]`. |

**Correspondance code** : `bridge.py::float_to_u16` et `bridge.py::u16_to_float`.

### 3.2 — Module `Formal/TierBoundary.lean` — INV-4

| Théorème | Propriété prouvée |
|:---|:---|
| `tier_verified_implies_conditions` | Si `assignTier` retourne `verified`, alors `score ≥ 8500 ∧ (models ≥ 3 ∨ hasAnchor)`. |

**Correspondance code** : `attestation.py` (logique d'assignation de tier).

**Red tests associés** (dans `RedTests.lean`) :

| Test | Propriété prouvée |
|:---|:---|
| `red_tier_1_low_score_not_verified` | score 5000, 5 modèles, anchor ⇒ **pas** verified. |
| `red_tier_2_no_anchor_few_models_not_verified` | score 8500, 1 modèle, pas d'anchor ⇒ **pas** verified. |
| `green_tier_1_high_score_many_models_verified` | score 8500, 3 modèles ⇒ verified (cas passant). |
| `green_tier_2_high_score_with_anchor_verified` | score 8500, anchor ⇒ verified (cas passant). |

### 3.3 — Module `Formal/SourceAnchor.lean` — INV-6

| Théorème | Propriété prouvée |
|:---|:---|
| `deterministic_requires_anchor` | Attestation well-formed + type deterministic ⇒ source_anchor non-nul. |
| `deterministic_without_anchor_not_wellformed` | Corollaire : deterministic sans anchor ⇒ non well-formed. |

**Correspondance code** : ADR-012 (bifurcation déterministe), `services/sources/adapters/`.

### 3.4 — Module `Formal/ClaimHash.lean` — INV-2

| Théorème | Propriété prouvée |
|:---|:---|
| `claim_hash_purity` | Deux attestations au noyau canonique identique ont le même hash. |
| `claim_hash_timestamp_independent` | Le timestamp n'entre pas dans l'identité d'un claim. |
| `claim_hash_submitter_independent` | Le submitter n'entre pas dans l'identité d'un claim. |

**Correspondance code** : `services/esmm/attestation.py::compute_claim_hash` (lignes 183-210).

**Red tests associés** :

| Test | Propriété prouvée |
|:---|:---|
| `red_hash_1_timestamp_independence` | Timestamps différents, même noyau ⇒ même hash. |
| `red_hash_2_submitter_independence` | Submitters différents, même noyau ⇒ même hash. |

**Importance architecturale** : INV-2 est la condition de possibilité d'ADR-017 (réseau de clusters). Sans cette propriété, deux clusters ne pourraient pas produire des attestations comparables sur le même claim.

## 4. Méthodologie de non-tautologie

### 4.1 — Le protocole de double falsification

Chaque invariant livré doit être accompagné d'au moins un red test qui **tombe** si l'invariant est cassé. La procédure de validation est :

1. **GREEN** : `lake build` passe avec l'invariant en place.
2. **RED** : on falsifie **temporairement** la définition de l'invariant (par exemple en abaissant un seuil, ou en affaiblissant une contrainte), on rebuild, le build **doit** échouer.
3. **RESTORE** : on restaure la définition originale, on rebuild, le build passe à nouveau.

Si l'étape RED ne produit pas d'échec, l'invariant est **tautologique** — sa preuve ne dépend pas de la propriété qu'elle prétend établir. Il doit être reformulé.

### 4.2 — Pourquoi cette exigence est non-négociable

La découverte du 2026-04-17 a révélé un cas concret d'invariant apparent mais réellement défaillant (TierBoundary incomplet, masqué par un RedTests orphelin). Sans double falsification systématique, ces faux positifs peuvent traverser le cycle de vie du projet pendant des mois.

Le coût marginal d'une falsification manuelle est de 5 minutes. Le coût d'une régression détectée en production (ou pire : d'une régression non détectée) est sans commune mesure.

### 4.3 — Ce que la CI garantit désormais

Depuis le commit du 2026-04-17 (`import Formal` dans `Main.lean`), `lake build` par défaut — la commande exécutée par `leanprover/lean-action@v1` dans la CI — compile l'**intégralité** de la lib, soit 18 jobs incluant tous les modules Lean et tous les red tests.

Toute régression future qui casserait un invariant ou un red test sera attrapée à la prochaine push. C'est un changement d'ordre de magnitude : avant, la CI compilait un `exe main` qui n'importait aucun module Lean.

## 5. Conformité modèle ↔ code — limites honnêtes

### 5.1 — Le gap sémantique (piège n°3 du brief)

Les preuves Lean 4 portent sur un **modèle** du protocole, pas sur le code qui l'implémente. Cette distinction est permanente avec les outils actuels : il n'existe pas en avril 2026 d'extraction automatique et fiable de Rust vers Lean 4. Le lien entre les définitions Lean et les fonctions Python/Rust est **humain**.

Conséquences pratiques :

- Une preuve Lean reste valide si le modèle est correct. Si le modèle diverge du code, la preuve est **sans valeur pour le runtime**, même si elle reste formellement correcte.
- La responsabilité de maintenir le lien modèle↔code repose sur les contributeurs (humains et agents IA). Cette responsabilité doit être explicitement reconnue, pas supposée.

### 5.2 — Vérifications de conformité actuelles

Pour chaque invariant livré, la conformité au code runtime a été vérifiée par **observation directe** au moment de la rédaction :

| Invariant | Vérification de conformité | Résultat |
|:---|:---|:---|
| INV-1 (Encoding) | Lecture `bridge.py::float_to_u16` et `u16_to_float` | ✅ signature et comportement alignés |
| INV-4 (TierBoundary) | Lecture de la logique d'assignation dans `attestation.py` | ⚠️ alignement vérifié visuellement, pas automatisé |
| INV-6 (SourceAnchor) | Contrôles ADR-012 dans les adapters | ⚠️ alignement vérifié visuellement |
| INV-2 (ClaimHash) | `grep` + lecture intégrale de `compute_claim_hash` lignes 183-210 | ✅ signature identique (4 champs canoniques, aucun autre) |

Ces vérifications sont des **observations ponctuelles**, pas des garanties continues. Une modification future du code Python ou Rust pourrait introduire une divergence sans que les preuves Lean ne la détectent.

### 5.3 — Écart connu et documenté : normalisation INV-2

Le code Python `compute_claim_hash` applique `.lower().strip()` à chaque champ avant concaténation (lignes 205-210). Le modèle Lean 4 ne modélise pas cette normalisation — il concatène les strings telles quelles.

Conséquence :

- Le code Python satisfait une propriété **plus forte** que le modèle Lean : « claims identiques après normalisation → même hash ».
- Le modèle Lean prouve : « claims identiques littéralement → même hash ».
- Les deux propriétés sont compatibles : la propriété Python implique la propriété Lean. Pas de divergence de sécurité.
- Une future version du modèle Lean pourrait inclure la normalisation pour resserrer la correspondance.

### 5.4 — Gap Rust : non comblé, documenté

La correspondance modèle Lean ↔ code Rust (programme Solana) n'est **pas** vérifiée dans cette version. Le programme Rust actuel ne calcule pas `claim_hash` — il le reçoit en paramètre et le stocke. Les invariants INV-4 et INV-6, s'ils devaient être enforcés on-chain dans une version future, nécessiteraient soit l'ajout de `require!` correspondants dans `lib.rs`, soit une vérification externe (Certora ou équivalent).

Cette limitation est acceptée et documentée. Elle sera levée lorsque :
- Les outils Rust↔Lean matureront (Aeneas, hax), **ou**
- Certora ajoutera un support stable d'Anchor 0.32, **ou**
- Les invariants concernés seront portés manuellement en `require!` avec test RED on-chain (comme fait pour l'Enum V2 dans ADR-019).

## 6. Ce qui est acquis — et pour quoi

### 6.1 — Par rapport à la roadmap

| Invariant | Utilité directe pour le projet |
|:---|:---|
| INV-1 (Encoding) | Garantit la cohérence des conversions float↔u16 utilisées partout : consensus_score, signature 5D, on-chain encoding. |
| INV-4 (TierBoundary) | Rend le tier `verified` formellement caractérisé. Un tier affiché comme `verified` satisfait nécessairement les conditions de promotion. |
| INV-6 (SourceAnchor) | Documente formellement la sémantique `deterministic` (ADR-012) : une attestation déterministe a nécessairement une source autoritaire. |
| INV-2 (ClaimHash) | **Condition de possibilité d'ADR-017.** Deux clusters indépendants produisent le même `claim_hash` pour le même claim, ce qui rend les queries cross-cluster possibles. |

### 6.2 — Pour un auditeur externe

Un reviewer qui consulte `Formal/` peut affirmer sans risque :

- Le protocole abstrait a 11 théorèmes formellement prouvés.
- Les preuves sont exercées par la CI à chaque push.
- Des red tests prouvent que les invariants ne sont pas tautologiques.
- Le lien entre les preuves et le code runtime est documenté et vérifié par observation, non mécaniquement garanti.

Ce niveau de garantie est **supérieur** à celui de la plupart des oracles et protocoles de consensus AI existants, qui n'ont aucune spécification formelle. Il est **inférieur** à celui de ChronosVault (100+ théorèmes) ou d'un smart contract Certora-verified.

## 7. Ce qui n'est pas prouvé (hors scope hackathon)

### 7.1 — Invariants identifiés mais non prouvés

| Invariant | Difficulté | Raison de l'exclusion |
|:---|:---|:---|
| INV-3 (PDA unicité) | Tier 1 | Garantie par la mécanique Solana elle-même ; une preuve Lean serait redondante et purement didactique. |
| INV-5 (Regression cut isolation) | Tier 2 | Vacueusement vrai dans l'architecture actuelle — aucune instruction ne compare deux attestations. Utile si une instruction future de comparaison est ajoutée. |
| INV-7 (Brier proper scoring) | Tier 3 | Nécessite mathlib (théorie de la mesure). Estimation 2-4 semaines pour un prouveur débutant. Hors scope hackathon. |
| INV-8 (Consensus convergence) | Tier 3 | Nécessite des axiomes sur l'indépendance conditionnelle des modèles. Théorème de théorie de la décision. Hors scope. |

### 7.2 — Propriétés qui restent conjecturales

- Absence de panic dans le code Rust (nécessiterait Certora ou Aeneas).
- Absence de overflow arithmétique sur les `u16`/`u8` côté Rust.
- Cohérence inter-frames : deux attestations du même claim avec deux frames différents ne sont pas directement comparables. Enforced par design (frame entre dans claim_hash), non prouvé formellement.

Ces propriétés peuvent devenir des ADR-021+ ultérieurs, selon l'évolution du projet et des outils disponibles.

## 8. Critères d'acceptation pour les invariants futurs

Tout nouvel invariant ajouté à `Formal/` doit satisfaire :

1. **Théorème prouvé sans `sorry`, `admit`, ni axiome ad hoc.**
2. **Au moins un red test associé** qui tombe si l'invariant est cassé (protocole §4.1).
3. **Red test inclus dans `lake build`** par import depuis `Formal.lean` (lesson learned RedTests orphelin).
4. **Vérification de conformité** : le code Python et/ou Rust correspondant est identifié par grep ou référence explicite, et les écarts éventuels sont documentés.
5. **Référence à un ADR** (existant ou nouveau) qui contextualise l'invariant dans l'architecture du projet.

Un invariant qui ne satisfait pas ces critères ne peut pas être présenté comme « prouvé » dans la documentation.

## 10. Remarques finales

Cet ADR clôt la première session structurée de vérification formelle du projet. Onze théorèmes prouvés, CI qui mord, red tests exercés, correspondance code documentée. C'est un acquis substantiel pour une infrastructure initialement montée en quelques jours.

L'ADR reconnaît également ses limites. La vérification formelle à l'état de l'art (Certora-grade) reste un objectif lointain, conditionné à la maturation d'outils externes. Le présent corpus de preuves n'y prétend pas.

L'honnêteté du présent document est elle-même un engagement : toute IA auditant ce projet à l'avenir, tout contributeur humain, tout reviewer académique, doit pouvoir lire cet ADR et calibrer **exactement** son niveau de confiance. Ni plus, ni moins.

C'est ce que le protocole EPP revendique pour ses attestations épistémiques. Il serait incohérent d'appliquer un standard moindre à sa propre documentation.
