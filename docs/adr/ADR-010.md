# ADR-010 : Traçabilité méthodologique du consensus
**Date** : 2026-02-15
**Statut** : Actif
**Dépendances** : ADR-005 (tiers multi-critères), ADR-007 (attestations append-only)

## Contexte

Une attestation EPP est un résultat expérimental. Elle affirme qu'un consensus
a été atteint sur un triplet donné, avec un score donné, par des modèles donnés.

Aujourd'hui l'attestation stocke le **résultat** (claim, score, votes, tier, signature_5d)
mais pas la **méthodologie** qui a produit ce résultat :

| Question | Stocké ? |
|----------|----------|
| Quelle fonction de pondération ? (Brier weighted? uniform?) | Non |
| Quelle version de normalisation des triplets ? | Non |
| Quel seuil de consensus appliqué ? | Non (dans esmm_runs.config, pas dans l'attestation) |
| Quel embedding model pour le merge sémantique ? | Non |
| Quel seuil de merge sémantique ? | Non |
| Les versions exactes des modèles (pas juste "latest") ? | Non |
| Les métriques de diagnostic (entropie, dispersion) ? | Non |
| Le consensus est-il contesté ? | Non (en cours, Phase 4.8) |

Sans ces informations, une attestation est un résultat scientifique publié sans
sa section méthodologie. Le `consensus_score = 0.72` ne signifie rien si on
ne sait pas comment il a été calculé. Et on ne peut pas répondre à la question :
"ce consensus tiendrait-il avec une autre stratégie ?"

Ce problème devient critique dès qu'on modifie la stratégie (ajout du semantic
merge, changement de normalisation, évolution des seuils). Les attestations
produites avant et après un changement ne sont pas comparables — mais rien
dans le schéma actuel ne permet de le savoir.

## Décision

### 1. Champ `consensus_meta TEXT` dans la table attestations

Un seul champ JSON, structuré en trois sections :

```json
{
  "methodology": {
    "consensus_method": "hash_exact_v2+semantic_merge_v1",
    "normalization_version": "normalize_triplet_v2_synonyms",
    "weighting_strategy": "brier_weighted",
    "merge_threshold": 0.85,
    "min_consensus": 0.5
  },
  "conditions": {
    "models": {
      "mistral:latest": {"resolved_version": "7b-v0.3", "weight": 0.82},
      "llama3.1:8b": {"resolved_version": "8b-instruct", "weight": 1.0},
      "deepseek-r1:latest": {"resolved_version": "7b", "weight": 0.65}
    },
    "embedding_model": "nomic-embed-text:latest",
    "cycles_completed": 5,
    "cycle_sequence": ["divergent", "divergent", "debate", "debate", "meta"]
  },
  "diagnostics": {
    "vote_entropy": 0.92,
    "semantic_dispersion": 0.34,
    "ambiguity_detected": false,
    "variations": [],
    "triplets_before_consensus": 48,
    "triplets_after_consensus": 7
  }
}
```

**Section `methodology`** — répond à "quelle fonction de pondération a produit ce consensus".

- `consensus_method` : identifiant versionné de la stratégie d'agrégation
- `normalization_version` : identifiant de la fonction normalize_triplet utilisée
- `weighting_strategy` : "brier_weighted" | "uniform" | futur
- `merge_threshold` : seuil cosinus pour le merge sémantique (null si inactif)
- `min_consensus` : seuil minimum d'agreement_ratio appliqué

**Section `conditions`** — répond à "dans quelles conditions expérimentales".

- `models` : chaque modèle avec sa version résolue et son poids effectif au moment du run
- `embedding_model` : modèle d'embedding utilisé pour le merge sémantique (null si inactif)
- `cycles_completed` : nombre de cycles ESMM effectivement complétés
- `cycle_sequence` : séquence exacte des cycles exécutés

**Section `diagnostics`** — répond à "ce consensus est-il reproductible".

- `vote_entropy` : entropie de Shannon sur la distribution des votes (0 = unanimité, élevé = désaccord)
- `semantic_dispersion` : dispersion cosinus moyenne entre les réponses des modèles
- `ambiguity_detected` : flag CONTESTED (cf. Phase 4.8)
- `variations` : formulations alternatives du cluster sémantique
- `triplets_before_consensus` : triplets validés avant filtrage par seuil
- `triplets_after_consensus` : triplets ayant survécu au consensus

### 2. Peuplement automatique

`pipeline.py` peuple `consensus_meta` au moment de la cristallisation, avant
l'appel à `db.store_attestation()`. Les données proviennent de :

- `ESMMRunConfig` → methodology + conditions
- `ConsensusEngine.compute_consensus()` → diagnostics
- `orchestrator._compute_model_weights()` → conditions.models.weight
- Ollama API `/api/show` → conditions.models.resolved_version (best effort)

### 3. Inclusion dans le hash et le portable_json

`consensus_meta` est inclus dans `portable_json` (sérialisé pour l'ancrage on-chain)
mais n'entre PAS dans le calcul de `claim_hash`. Le claim_hash identifie le triplet
canonique ; les métadonnées méthodologiques sont des annotations, pas de l'identité.

Ceci est cohérent avec ADR-007 : le contenu épistémique (triplet + score) est
immuable. Les métadonnées méthodologiques sont de la provenance, pas du contenu.

### 4. Versionnement des stratégies

Chaque changement de stratégie de consensus incrémente `consensus_method` :

| Version | Description |
|---------|-------------|
| `hash_exact_v1` | Hash SHA-256 sur (lower(s), lower(r), lower(o)). Pré-R2. |
| `hash_exact_v2` | Hash après normalize_triplet (synonymes, abréviations). R2. |
| `hash_exact_v2+semantic_merge_v1` | Passe 1 hash exact + passe 2 embedding cosinus. Phase 4.8. |

Toute attestation future porte sa version de consensus. Deux attestations avec
des `consensus_method` différents ne sont pas directement comparables sans
connaissance des deux stratégies.

## Conséquences

### Obligations pour Claude Code

1. **NE JAMAIS** produire une attestation sans `consensus_meta` peuplé.
   Une attestation sans méthodologie est un résultat sans preuve.

2. **NE JAMAIS** modifier la stratégie de consensus sans incrémenter
   `consensus_method`. Chaque changement doit être traçable.

3. **NE JAMAIS** stocker "latest" comme version de modèle dans
   `conditions.models` si la version résolue est disponible via l'API Ollama.
   "latest" est un alias, pas une version.

4. **TOUJOURS** recalculer `vote_entropy` et `semantic_dispersion` pour
   chaque attestation. Ces métriques ne sont pas optionnelles — elles
   sont le signal de reproductibilité.

5. **TOUJOURS** inclure `consensus_meta` dans `portable_json`.

### Zones ouvertes (COMMUNITY_DECISION_REQUIRED)

- Le format exact de `consensus_meta` peut évoluer. Les champs listés ci-dessus
  sont le minimum. La communauté peut ajouter des champs (hardware fingerprint,
  température de sampling, etc.).

- La comparabilité inter-versions : comment comparer une attestation `hash_exact_v1`
  avec une `hash_exact_v2+semantic_merge_v1` sur le même triplet ? Politique de
  revalidation automatique vs manuelle à définir par la communauté.

- Les seuils diagnostiques : à partir de quelle `vote_entropy` un consensus est
  considéré fragile ? Ce seuil devrait être déterminé empiriquement par la
  communauté sur la base de données réelles, pas fixé par l'équipe fondatrice.

### Compatibilité

- ADR-005 : le `confidence_tier` est calculé indépendamment de `consensus_meta`.
  Les deux coexistent. `consensus_meta` explique *comment* on a obtenu le score
  qui a déterminé le tier.

- ADR-007 : `consensus_meta` est écrit une fois à la cristallisation et ne change
  jamais. Cohérent avec append-only.

- Phase 4.8 (Language Neutrality) : `ambiguity_detected` et `variations` dans
  `diagnostics` sont les mêmes champs que ceux définis dans les instructions
  Phase 4.8. ADR-010 les ancre formellement dans le schéma.

## Implémentation

### Schema SQL

```sql
ALTER TABLE attestations ADD COLUMN consensus_meta TEXT;
```

### Priorité

Ce champ doit être ajouté AVANT toute campagne de questions à grande échelle.
Les attestations produites sans `consensus_meta` seront des données orphelines
impossibles à contextualiser rétroactivement.

### Migration des attestations existantes

Les attestations pré-ADR-010 (s'il en existe) reçoivent :

```json
{"methodology": {"consensus_method": "hash_exact_v1", "note": "pre-ADR-010, metadata unavailable"}}
```

Ceci est honnête : on sait qu'on ne sait pas.
