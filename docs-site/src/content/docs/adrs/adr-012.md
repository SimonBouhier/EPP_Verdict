## Contexte

L'intégration de sources RWA institutionnelles (sanctions, registres carbone) expose une classe de claims absente du modèle actuel : les **claims déterministes**. L'entité X est ou n'est pas sur la liste OFAC. Le crédit VCU #N est ou n'est pas émis et non-retiré. Ces faits ont une autorité unique qui fait foi — soumettre un tel claim au pipeline ESMM introduit de la fausse incertitude dans un fait objectif et dégrade la performance sans valeur ajoutée.

Le code actuel ne distingue pas la nature épistémique d'un claim (délibératif vs déterministe). `claim_type` dans VERIFY mode approche la bonne granularité mais n'intègre pas la notion de source autoritaire externe. Le champ `source_anchor` (32 bytes) existe déjà on-chain dans `EpistemicAttestation` — il est sous-exploité.

## Décision

### Bifurcation explicite dans `ESMMRunConfig`

```python
class ClaimNature(str, Enum):
    EPISTEMIC     = "epistemic"      # Pipeline ESMM complet (défaut)
    DETERMINISTIC = "deterministic"  # Lookup source autoritaire, bypass ESMM
```

`ESMMRunConfig` reçoit deux champs optionnels : `claim_nature` (défaut `EPISTEMIC`) et `source_anchor_spec`. Si `claim_nature = DETERMINISTIC` sans `source_anchor_spec` → erreur à l'initialisation. Le choix est **déclaré par l'appelant**, jamais inféré automatiquement (Axiome 3).

### Nouveau module `services/esmm/source_anchor_builder.py`

Responsabilité unique : interroger une source externe, valider la réponse, et produire un `SourceAnchorResult`.

```python
@dataclass
class SourceAnchorSpec:
    source_id: str           # "ofac_sdn" | "opensanctions" | "verra_vcs" | "eu_cfsp"
    frame_id: str            # Frame métrologique associé
    query: Dict[str, Any]    # Paramètres de la requête
    max_age_hours: int = 24  # TTL — au-delà, re-fetch obligatoire
    min_sources: int = 1     # Sources concordantes requises pour tier "verified"

@dataclass
class SourceAnchorResult:
    source_id: str
    raw_response: Dict[str, Any]       # JSON complet — stocké off-chain (SQLite)
    normalized_result: Dict[str, Any]  # {"status": "clear"|"match", "score": float}
    source_anchor: str                 # SHA-256(raw_response canonique) → on-chain
    fetched_at: float
    source_version: str                # Ex: "OFAC-2026-02-25"
    is_fresh: bool
```

**Le `source_anchor` est le SHA-256 du `raw_response` sérialisé en JSON canonique (sorted keys, compact).** C'est cette valeur qui part on-chain. Le `raw_response` complet reste en SQLite (nouvelle table `source_anchor_snapshots`).

### Quatre adaptateurs dans `services/sources/adapters/` [Renommé depuis `services/rwa/` — ADR-014 §2.1]

Interface commune `SourceAdapter` (fetch + normalize + get_source_version). Implémentations :

| Adaptateur | Source | Endpoint |
|:---|:---|:---|
| `OpenSanctionsAdapter` | OpenSanctions (yente) | POST `/match` |
| `OfacAdapter` | OFAC SDN (US Treasury) | POST `/screening` |
| `EuCfspAdapter` | EU CFSP / Sanctions.network | GET `/sanctions` |
| `VerraVcsAdapter` | Verra VCS Registry | GET `/projects/{id}` + `/credits/{serial}` |

Les adaptateurs sont de purs wrappers HTTP sans logique métier.

### Trois nouveaux `MetrologicalFrame`

**`compliance_sanctions_v1.0`** — domaine `regulatory_compliance`, metric `sanctions_status`. Paramètres clés : `authoritative_sources: [OFAC_SDN, EU_CFSP, UN, opensanctions]`, `match_score_threshold: 0.85`, `snapshot_ttl_hours: 24`, `esmm_bypass: true`. Tier assigné par `required_sources` (1 → `proposition`, 2 concordantes → `validated`, 3 + score ≥ 0.95 → `verified`).

**`carbon_credits_vcs_v1.0`** — domaine `environmental_assets`, metric `carbon_credit_validity`. Deux couches explicites : L1 déterministe (serial lookup, `esmm_bypass: true`) et L2 épistémique optionnelle (soundness méthodologique, `esmm_bypass: false`, désactivée par défaut). L1 et L2 produisent deux attestations liées par `previous_hash` (ADR-006). L2 ne peut pas exister sans L1 validée.

**`rwa_identity_v1.0`** — frame généraliste pour combiner plusieurs sources. Si le score de la source déterministe est ambigu (< seuil configurable), déclenche optionnellement une couche ESMM pour analyse contextuelle. Seul frame où les deux chemins s'enchaînent automatiquement.

### Impact sur `consensus_meta` (ADR-010)

Toute attestation déterministe porte une section `source_anchor_meta` dans `consensus_meta` :

```json
{
  "methodology": {
    "consensus_method": "deterministic_source_v1",
    "esmm_invoked": false
  },
  "source_anchor_meta": {
    "source_id": "ofac_sdn",
    "source_version": "OFAC-2026-02-25",
    "fetched_at": 1740470701,
    "is_fresh": true,
    "snapshot_id": "uuid"
  },
  "diagnostics": {
    "sources_checked": 2,
    "concordant_sources": 2,
    "result": "clear"
  }
}
```

Validation à la cristallisation : absence de ce bloc sur une attestation `deterministic_source` → rejet.

### Nouvelle table SQL

```sql
CREATE TABLE IF NOT EXISTS source_anchor_snapshots (
    snapshot_id    TEXT PRIMARY KEY,
    source_id      TEXT NOT NULL,
    source_version TEXT NOT NULL,
    query_hash     TEXT NOT NULL,   -- SHA-256(canonical query JSON)
    raw_response   TEXT NOT NULL,   -- JSON complet
    source_anchor  TEXT NOT NULL,   -- SHA-256(raw_response) → on-chain
    fetched_at     REAL NOT NULL,
    frame_id       TEXT NOT NULL,
    UNIQUE (source_id, query_hash, source_version)
);
```

## Conséquences

### Ce qui change

| Composant | Modification |
|:---|:---|
| `services/esmm/source_anchor_builder.py` | **NOUVEAU** |
| `services/sources/adapters/` | **NOUVEAU répertoire** — 4 adaptateurs [Renommé depuis `services/rwa/` — ADR-014 §2.1] |
| `services/solana/metrological_frame.py` | +3 frames |
| `services/esmm/orchestrator.py` | `ESMMRunConfig` +`claim_nature` +`source_anchor_spec`, bifurcation en début de `execute_cycles()` |
| `services/esmm/attestation.py` | `crystallize()` : gestion `attestation_mode = "deterministic_source"` dans `consensus_meta` |
| `database/schema.sql` | +table `source_anchor_snapshots` |
| `database/engine.py` | +`store_source_anchor_snapshot()`, `get_snapshot_by_anchor()`, `is_snapshot_fresh()` |
| `config.yaml` | +section `sources.adapters` (TTL, credentials via env vars, enable/disable par adaptateur) [Renommé depuis `rwa.sources` — ADR-014 §2.1] |
| `cli/epp_cli.py` | +commande `epp verify-rwa --source --entity --frame` |

### Ce qui ne change pas

- Structure on-chain `EpistemicAttestation` (462 bytes) — `source_anchor` existe déjà
- Claim hash (ADR-006) — immuable
- Cycles ESMM ASSESS/CHALLENGE/ADJUDICATE — inchangés pour le chemin épistémique
- Interface `run_pipeline()` — transparent si `claim_nature` non spécifié

### Risques

| Risque | Mitigation |
|:---|:---|
| Credentials API exposés | Env vars uniquement, jamais en config.yaml versionné |
| Snapshot périmé | TTL conservateur 24h. Cache SQLite évite les re-fetch inutiles |
| API Verra VCS schéma instable | Versionnage adaptateur (`VerraVcsAdapterV1`). Bump force re-attestation |
| Confusion déterministe / épistémique par un consommateur | `consensus_meta.methodology.esmm_invoked` lisible off-chain dans SQLite |

### Questions ouvertes — COMMUNITY_DECISION_REQUIRED

**Q1** — Frais différenciés déterministe vs épistémique ? Vecteur de paiement (SOL, USDC, token EPP) ?

**Q2** — Qui garantit l'intégrité du `raw_response` avant hash ? TEE ou ZKP hors périmètre ADR-012 — à poser avant mainnet.

**Q3** — Durée de validité on-chain d'une attestation déterministe. Un crédit attesté "non-retiré" à T peut l'être à T+30j. Quel mécanisme déclenche la revalidation ?

## Ordre d'implémentation recommandé

1. `source_anchor_builder.py` + `OpenSanctionsAdapter` (0 credential, open-source, testable immédiatement)
2. Frame `compliance_sanctions_v1.0` + tests RED-GREEN-FIX bypass
3. `ESMMRunConfig.claim_nature` + bifurcation orchestrateur
4. Table `source_anchor_snapshots` + migration
5. `OfacAdapter` + `EuCfspAdapter`
6. `VerraVcsAdapter` L1 seul
7. Frame VCS + chaînage L1/L2 quand L1 stable
