## 1. Contexte

### 1.1 — Le problème : chaque run repart de zéro

Aujourd'hui, le pipeline ESMM traite chaque claim comme si le système n'avait aucune mémoire. Quand trois LLMs évaluent "Donald Trump won the 2024 US presidential election", ils produisent CONTESTED à 0.43 — leur knowledge cutoff les rend aveugles. Quand Wikidata confirme le fait à 0.85 via le chemin déterministe, les deux attestations coexistent on-chain. Mais le savoir acquis par la source déterministe ne profite jamais aux LLMs.

Le run suivant sur le même claim, ou sur un claim connexe, repart de la même ignorance. Le graphe accumule du savoir vérifié que personne ne consomme.

### 1.2 — L'observation fondatrice

Le run `jiang_20260311_082057.json` illustre le gaspillage :

| Chemin | Score | Temps |
|:---|:---|:---|
| VERIFY (3 LLMs) | 0.43 CONTESTED | ~104s |
| DETERMINISTIC (Wikidata) | 0.85 found | ~2s |

Si les LLMs avaient eu accès au résultat Wikidata dans leur contexte, le verdict aurait été significativement différent. Pas parce qu'on force la réponse — mais parce que l'information vérifiée est disponible et que ne pas la fournir est un choix de design, pas une contrainte technique.

### 1.3 — Le concept : Flywheel Épistémique

Un **flywheel** (volant d'inertie) est un mécanisme qui accumule de l'énergie à chaque rotation et la restitue au cycle suivant. Le Flywheel Épistémique applique ce principe au graphe de connaissances EPP :

1. **Accumulation** — Chaque attestation déterministe enrichit le graphe avec du savoir vérifié, horodaté, hashé.
2. **Restitution** — Avant la délibération LLM, le pipeline consulte le graphe pour les attestations déterministes existantes sur le même `claim_hash`.
3. **Injection** — Les résultats trouvés sont injectés dans le prompt système des LLMs comme contexte factuel vérifié.
4. **Amplification** — Les LLMs délibèrent avec une base factuelle plus solide, produisant des verdicts plus précis, qui à leur tour enrichissent le graphe.

Le graphe devient plus intelligent à chaque cycle sans réentraîner aucun modèle.

## 2. Décision

### 2.1 — Principe : le graphe alimente le pipeline qui alimente le graphe

Avant la boucle de cycles ESMM (ASSESS → CHALLENGE → ADJUDICATE en mode VERIFY), le pipeline effectue un lookup dans la base de données locale pour trouver les attestations déterministes existantes portant le même `claim_hash`.

Si des attestations déterministes existent, leurs résultats sont formatés et injectés dans le prompt système comme section `[VERIFIED DATA]`.

Les LLMs restent libres de contester les données — l'injection est informative, pas prescriptive. Le verdict final peut diverger de la source déterministe, et cette divergence est elle-même un signal (Axiome 5).

### 2.2 — Lookup des ancres existantes

```python
async def _lookup_existing_anchors(
    claim_hash: str,
    db: "DatabasePool",
) -> list[dict]:
    """
    Cherche les attestations déterministes existantes pour un claim_hash.

    Returns:
        Liste de dicts {source_id, score, status, results, fetched_at, source_version}
        triée par date (plus récente en premier).
    """
    query = """
        SELECT subject, predicate, object, consensus_score,
               consensus_meta, created_at
        FROM attestations
        WHERE claim_hash = ?
          AND json_extract(consensus_meta, '$.methodology.claim_nature') = 'deterministic'
        ORDER BY created_at DESC
        LIMIT 5
    """
    rows = await db.fetch_all(query, (claim_hash,))

    anchors = []
    for row in rows:
        meta = json.loads(row["consensus_meta"]) if isinstance(row["consensus_meta"], str) else row["consensus_meta"]
        source_meta = meta.get("source_anchor_meta", {})
        anchors.append({
            "source_id": source_meta.get("source_id", "unknown"),
            "score": row["consensus_score"],
            "status": source_meta.get("normalized", {}).get("status", "unknown"),
            "results": source_meta.get("normalized", {}).get("results", []),
            "fetched_at": source_meta.get("fetched_at", row["created_at"]),
            "source_version": source_meta.get("source_version", "unknown"),
        })

    return anchors
```

### 2.3 — Injection dans le prompt système

```python
def _format_anchor_context(anchors: list[dict]) -> str:
    """
    Formate les ancres déterministes pour injection dans le prompt LLM.

    Le format est informatif, pas prescriptif. Les LLMs sont libres
    de contester les données — la divergence est le signal.
    """
    if not anchors:
        return ""

    lines = ["[VERIFIED DATA — from deterministic sources, for context]"]
    for a in anchors:
        results_str = ""
        if a["results"]:
            # Extraire les valeurs lisibles (ex: "winnerLabel: Donald Trump")
            for r in a["results"][:3]:  # Max 3 résultats
                results_str += ", ".join(f"{k}: {v}" for k, v in r.items() if k != "item")

        lines.append(
            f"- Source: {a['source_id']} | Status: {a['status']} | "
            f"Score: {a['score']} | Data: {results_str} | "
            f"Fetched: {a['fetched_at']} | Version: {a['source_version']}"
        )

    lines.append("[END VERIFIED DATA — you may contest these findings if your analysis disagrees]")
    return "\n".join(lines)
```

### 2.4 — Point d'injection dans pipeline.py

Dans `run_pipeline()`, **après** le calcul du `claim_hash` et **avant** la boucle de cycles :

```python
# --- Flywheel: lookup existing deterministic anchors (ADR-018) ---
anchors = await _lookup_existing_anchors(claim_hash, db)
anchor_context = _format_anchor_context(anchors)

if anchor_context:
    logger.info(f"[Flywheel] Found {len(anchors)} deterministic anchor(s) for claim_hash={claim_hash[:12]}...")
    # Inject into system prompt for all subsequent cycles
    flywheel_injection = anchor_context
else:
    flywheel_injection = ""
```

Le `flywheel_injection` est concaténé au prompt système de chaque cycle (ASSESS, CHALLENGE, ADJUDICATE). Il apparaît comme contexte factuel, pas comme instruction.

### 2.5 — Traçabilité dans consensus_meta

L'injection flywheel est documentée dans `consensus_meta` pour garantir la reproductibilité (Axiome 3) :

```python
consensus_meta["methodology"]["flywheel"] = {
    "enabled": True,
    "anchors_found": len(anchors),
    "sources_injected": [a["source_id"] for a in anchors],
    "injection_timestamp": datetime.now(timezone.utc).isoformat(),
}
```

Si aucune ancre n'est trouvée :

```python
consensus_meta["methodology"]["flywheel"] = {
    "enabled": True,
    "anchors_found": 0,
    "sources_injected": [],
}
```

Cela permet de distinguer explicitement :
- **Attestation sans flywheel** (runs historiques) : clé `flywheel` absente
- **Attestation avec flywheel, aucune ancre** : `anchors_found: 0`
- **Attestation avec flywheel, ancres injectées** : `anchors_found: N, sources_injected: [...]`

Deux attestations produites avec et sans flywheel sur le même claim sont **explicitement non comparables** (Axiome 3). Le `consensus_meta` le documente.

## 4. Ce qui ne change pas

- **Chemin déterministe (ADR-012)** — inchangé. Le flywheel consomme les attestations déterministes, il ne les modifie pas.
- **Claim hash (ADR-006)** — immuable. Le flywheel cherche par claim_hash existant.
- **Structure on-chain** — aucune modification. Les PDA restent identiques.
- **Tiers de confiance (ADR-005)** — inchangés. Le flywheel peut améliorer le score, mais le tier est calculé avec les mêmes règles.
- **Mode EXPLORE** — non concerné. Le flywheel ne s'active qu'en mode VERIFY (claims factuels).

## 5. Démonstration attendue

### Run sans flywheel (existant) :

```
JIANG-RESOLVED-01: "Donald Trump won the 2024 US presidential election"
  VERIFY:        0.43 CONTESTED (LLMs ignorent le résultat)
  DETERMINISTIC: 0.85 found (Wikidata confirme)
```

### Run avec flywheel (après ADR-018) :

```
JIANG-RESOLVED-01: "Donald Trump won the 2024 US presidential election"
  Flywheel lookup: 1 anchor found (wikidata, score=0.85, "Donald Trump")
  VERIFY:        0.80+ SUPPORTED (LLMs informés par la source vérifiée)
  Δ = +0.37 — même modèles, même claim, graphe plus intelligent
```

Le delta avant/après flywheel est la métrique de démonstration. Il prouve que le protocole s'améliore avec le temps sans réentraîner aucun modèle.

## 6. Garde-fous

### 6.1 — L'injection est informative, pas prescriptive

Le prompt dit explicitement : *"you may contest these findings if your analysis disagrees."* Un LLM qui conteste une source déterministe produit un signal de second ordre précieux — ça peut indiquer une source périmée, un QID erroné, ou un claim dont la ground truth a changé.

### 6.2 — Pas de boucle auto-référentielle

Le flywheel ne réinjecte que les attestations **déterministes** (claim_nature = "deterministic"). Il ne réinjecte jamais les attestations VERIFY dans le prompt d'un autre VERIFY. Aucun modèle ne voit son propre verdict précédent — seulement les données de sources externes.

### 6.3 — Fraîcheur des ancres

L'ancre la plus récente est priorisée (`ORDER BY created_at DESC`). Si une source déterministe est mise à jour (ex: Wikidata corrigée), la nouvelle ancre prend le dessus. Les ancres anciennes restent dans la DB mais ne sont pas injectées si une version plus récente existe.

### 6.4 — Désactivation

`config.yaml : flywheel.enabled: false` désactive le mécanisme. Les runs sans flywheel restent possibles et comparables aux runs historiques.

## 7. Risques

| Risque | Probabilité | Mitigation |
|:---|:---|:---|
| Ancre erronée propagée (QID faux, source corrompue) | Faible | Les LLMs peuvent contester. Le MAX_CONFIDENCE des sources (0.85 Wikidata) empêche le score d'atteindre 1.0. La divergence LLMs vs ancre est loguée. |
| Biais de confirmation : LLMs suivent aveuglément l'ancre | Moyenne | Le prompt explicite le droit de contester. Le vote_entropy mesurera si les LLMs délibèrent réellement ou se conforment. Un entropy < 0.5 avec ancre injectée signalerait un conformisme excessif. |
| Surcharge du prompt avec trop d'ancres | Faible | Limité à 5 ancres, 3 résultats par ancre. Budget tokens estimé : ~200 tokens max. |
| Confusion entre runs avec et sans flywheel | Moyenne | Traçabilité explicite dans consensus_meta (§2.5). Axiome 3 respecté. |

## 8. Lien avec ADR-017 (Clusters)

Dans un réseau multi-clusters, le flywheel devient encore plus puissant :

- Le **Cluster A** produit une attestation déterministe via Wikidata.
- Le **Cluster B**, interrogeant le même claim avec des modèles différents, trouve l'ancre du Cluster A on-chain via `getProgramAccounts` + filtre `claim_hash`.
- Le Cluster B injecte l'ancre dans ses propres LLMs.
- Le réseau entier bénéficie de chaque attestation déterministe produite par n'importe quel cluster.

Le flywheel est intra-cluster en Phase 1 (DB locale). Il devient inter-clusters en Phase 2 (on-chain lookup). Le code est le même — seule la source du lookup change (SQLite local → Solana getProgramAccounts).

## 10. Métrique de succès

Le flywheel est considéré comme fonctionnel si :

- **JIANG-RESOLVED-01** passe de CONTESTED (~0.43) à SUPPORTED (>0.70) avec flywheel activé
- **Le vote_entropy reste > 0.7** (les LLMs délibèrent encore, pas de conformisme aveugle)
- **Le consensus_meta documente correctement** l'injection (sources_injected non vide)
- **Les tests passent** sans régression (baseline 801 maintenue)
