**Date**: 2026-02-12
**Status**: Active

## Context
The EPP pipeline submits epistemic attestations on-chain via a local Solana keypair. The submitter signs every transaction — its pubkey is stored in the attestation as proof of origin.

## Decision

### Keypair management
- The keypair is loaded from an unencrypted JSON file (`~/.config/solana/id.json` by default, configurable via `keypair_path`).
- Only the pubkey is logged (`AUDIT[A10-021]`). The private key is NEVER exposed in logs, configs, or API responses.
- In CI/devnet, use a dedicated keypair for the pipeline (not the personal keypair).

### Signature and verification
- Anchor enforces that the submitter is `Signer` on the `submit_attestation` instruction (`lib.rs:124`). Only the keypair holder can submit.
- The `submitter` field in the on-chain attestation is the pubkey of the signer, verified by the Solana runtime.
- No delegation: one keypair = one submitter. For multiple submitters, deploy multiple keypairs.

### Restrictions
- **Devnet/localnet only**: `validate_cluster()` forbids mainnet (`config.py`). The `SolanaCluster` enum has no MAINNET value.
- **No on-chain rate limiting**: rate limiting is on the pipeline side (an ESMM run produces N attestations, no more). The Anchor program does not throttle per-submitter.
- **Challenge**: any keypair holder can challenge an existing attestation. The challenge creates a new attestation linked to the challenged PDA.

### Accepted risks
- `AUDIT[A10-009]`: keypair as unencrypted JSON. Acceptable for devnet. For mainnet (future), require an HSM or hardware wallet.
- `AUDIT[A10-008]`: the devnet guard is client-side, not on-chain. An attacker can bypass it via direct RPC. Acceptable because the program is deployed on devnet only.

## Consequences
- Do NOT deploy on mainnet without migrating to encrypted keypair / HSM.
- Do NOT add delegation without a new ADR.
- Document the dedicated keypair in the deployment README.
