## 1. Contexte

### 1.1 — L'opportunité

Le pipeline VERIFY existant (ASSESS → CHALLENGE → ADJUDICATE) se transpose mécaniquement sur l'audit de smart contracts. Chaque claim porte sur la présence ou l'absence d'une vulnérabilité dans une portion de code. Les mesures d'incertitude épistémique (consensus_score, vote_entropy, dissent_score, Brier scores) permettent de comparer objectivement les performances des modèles avec les audits humains de référence.

La disponibilité de **ground truth public** (rapports Trail of Bits, OpenZeppelin, PeckShield, Solodit) rend EPP benchmarkable quantitativement pour la première fois. L'entropie de vote devient un signal de découverte : haute entropie sur une fonction = zone à investiguer, exactement comme un auditeur humain concentre son attention sur le code inhabituel.

### 1.2 — Validation SoTA : alignement avec Trail of Bits (mars 2026)

L'approche EPP est validée par les pratiques de Trail of Bits, leader mondial de l'audit de smart contracts :

- **`entry-point-analyzer`** (plugin Claude Code, trailofbits/skills) : identifie les fonctions state-changing, les classifie par niveau d'accès (public/admin/role-restricted/contract-only), exclut les view/pure/read-only. C'est exactement le rôle de notre `contract_slicer.py`. Notre slicer s'en inspire mais produit des `ContractUnit` formatées pour le pipeline VERIFY au lieu de rapports textuels.

- **`building-secure-contracts`** : 11 skills spécialisés couvrant 6 blockchains + 5 assistants de guidelines. Le framework de maturité en 9 catégories (arithmetic safety, access controls, complexity, MEV risks, etc.) est un axe d'extension futur pour EPP (voir §8, Q5).

- **Slither `--print entry-points`** : liste nativement les entry-points state-changing avec leurs variables d'état. Quand Slither est disponible, notre slicer peut l'utiliser comme première passe au lieu du parsing regex, puis enrichir avec le contexte (imports, héritage, modifiers).

- **Format d'audit Trail of Bits** (cf. audit LooksRare 2022, 15 findings) : Finding + Severity (High/Medium/Low/Informational — 4 niveaux, pas 5) + Vulnerability Class (Access Controls, Timing, Undefined Behavior, Patching, Data Validation, Auditing/Logging, Configuration, Cryptography) + Response (Acknowledged/Rejected + Additional Comments). Notre format de sortie supporte à la fois la taxonomie SWC et les classes Trail of Bits (voir §2.2).

- **`crytic/not-so-smart-contracts`** : exemples de vulnérabilités réelles avec code source annoté, maintenu par Trail of Bits. Dataset de référence prioritaire pour notre benchmark (code + description + pattern vulnérable + recommandation).

**Ce que EPP ajoute par rapport à l'état de l'art** : les skills Trail of Bits sont des workflows single-model (Claude Code). EPP est le seul système qui soumet la même fonction à N modèles architecturalement distincts, mesure leur désaccord (vote_entropy), et ancre le consensus quantifié on-chain. Le delta entre un audit single-model et un audit multi-modèle EPP est mesurable et constitue la proposition de valeur unique.

### 1.3 — La contrainte technique immédiate : context window

Les modèles locaux (mistral ~8K, llama3.1 ~8-128K, deepseek-r1 ~64K via Ollama) ne peuvent pas ingérer un contrat entier de plusieurs milliers de lignes en tant que contexte de prompt. Même les modèles avec des fenêtres théoriquement larges dégradent significativement leur qualité d'attention au-delà de ~4K tokens de code source.

**Choix architectural immédiat : décomposition par fonction.** Le contrat est pré-découpé en unités atomiques (fonctions, modificateurs, constructeurs), chacune soumise comme une claim indépendante au pipeline VERIFY.

**Ce choix est explicitement provisoire.** L'architecture DOIT préserver la possibilité future de soumettre un contrat entier via des APIs à grande fenêtre contextuelle (GPT-4, Claude, Gemini). Le module de découpe est un composant isolé et remplaçable, pas une hypothèse enfouie dans le pipeline. Deux branches coexisteront à terme : la branche `function_level` (légère, compatible petits modèles locaux) et la branche `full_contract` (APIs cloud, contexte large). La première ne disparaît jamais — elle reste le fallback universel.

### 1.4 — Le double chemin : épistémique + déterministe

L'audit de smart contracts combine naturellement les deux chemins d'EPP :

- **Chemin épistémique (ESMM)** : Les modèles délibèrent sur les vulnérabilités sémantiques — reentrancy, access control, business logic flaws. C'est le cœur de la valeur ajoutée : le désaccord entre modèles signale les zones ambiguës.

- **Chemin déterministe (ADR-012)** : Les outils d'analyse statique (Slither, Mythril, Solhint) produisent des résultats binaires et reproductibles. Ils sont intégrés comme sources autoritaires via le pattern `SourceAdapter` existant.

Les deux chemins produisent des attestations distinctes liées par `previous_hash` (ADR-006). Le chemin déterministe renforce le signal sans polluer le consensus épistémique.

## 2. Décision

### 2.1 — Pré-requis : Migration `services/rwa/` → `services/sources/`

Le répertoire `services/rwa/adapters/` contient les adaptateurs de sources autoritaires (OpenSanctions, OFAC, EU CFSP, Verra VCS). Avec l'ajout de Slither et des futures sources d'audit, le nom `rwa` (Real World Assets) est trompeur. 

**Renommage** : `services/rwa/` → `services/sources/`. Tous les imports sont mis à jour. Cette migration est un **chantier isolé et bloquant** qui doit être exécuté et audité avant toute implémentation ADR-014.

**Procédure** :
1. Claude Code produit un script de diagnostic listant tous les imports `services/rwa` dans le projet (`grep -rn "services/rwa\|services.rwa\|from.*rwa" --include="*.py"`)
2. Sim transmet les résultats à Opus pour validation du périmètre
3. Claude Code exécute le renommage structuré (répertoire + imports + tests + config)
4. Audit C1 complet (signatures fantômes) post-migration
5. `pytest tests/` complet — baseline inchangée

### 2.2 — Module de décomposition : `contract_slicer.py`

**Responsabilité unique** : recevoir un fichier source (.sol ou .rs), extraire les unités auditables, et produire une liste de claims formatées pour le pipeline VERIFY.

```python
@dataclass
class ContractUnit:
    """Unité atomique extraite d'un smart contract."""
    unit_id: str                    # hash(contract_path + function_name)
    contract_path: str              # Chemin du fichier source
    contract_name: str              # Nom du contrat (ex: "TokenVault")
    unit_type: str                  # "function" | "modifier" | "constructor" | "fallback"
    unit_name: str                  # Nom de la fonction (ex: "withdraw")
    source_code: str                # Code source brut de l'unité
    visibility: str                 # "public" | "external" | "internal" | "private"
    access_level: str               # "public" | "admin" | "role_restricted" | "contract_only"
                                    # (aligné Trail of Bits entry-point-analyzer)
    modifiers: List[str]            # Modificateurs appliqués (ex: ["onlyOwner", "nonReentrant"])
    state_writes: List[str]         # Variables d'état modifiées (extraction statique)
    external_calls: List[str]       # Appels externes détectés (extraction statique)
    line_range: Tuple[int, int]     # Lignes début-fin dans le fichier source
    context_imports: str            # Imports et héritages pertinents (max 500 tokens)

@dataclass 
class ContractSliceResult:
    """Résultat du découpage d'un contrat."""
    contract_path: str
    contract_hash: str              # SHA-256 du fichier source complet
    language: str                   # "solidity" | "rust_anchor"
    units: List[ContractUnit]
    total_lines: int
    slice_strategy: str             # "function_level_v1" — versionné (Axiome 3)
    skipped_units: List[str]        # Unités ignorées (ex: pure view sans state)
    slither_assisted: bool          # True si Slither entry-points a été utilisé
```

**Stratégie de découpe `function_level_v1`** :

1. **Parser** : deux modes. Mode Slither (si disponible) : `slither <path> --print entry-points --json -` fournit les fonctions state-changing, leurs variables, et leur visibilité. Mode regex fallback : patterns robustes pour Solidity (function/modifier/constructor/fallback/receive), AST-lite pour Rust Anchor (#[instruction]). Pas de dépendance obligatoire à un compilateur externe.
2. **Classification d'accès** : alignée sur Trail of Bits entry-point-analyzer — `public` (aucun modifier restrictif), `admin` (onlyOwner/onlyAdmin), `role_restricted` (RBAC, AccessControl), `contract_only` (internal + external calls from known contracts).
3. **Enrichissement** : chaque unité est annotée avec ses `state_writes` et `external_calls` (extraction statique par grep sur le corps de la fonction). Ces annotations alimentent le prompt ASSESS.
4. **Contexte** : les imports, héritages et déclarations de storage sont ajoutés en préambule compact (`context_imports`, cap 500 tokens) pour donner aux modèles le contexte de contrat minimal.
5. **Filtrage** : les fonctions `pure`/`view` sans appels externes sont marquées `low_priority` (auditées si le budget de tokens le permet, skippées sinon).

**Chemin futur — `full_contract_v2`** : un second `slice_strategy` à implémenter quand les APIs à grande fenêtre sont disponibles. Le contrat entier est passé comme un seul bloc avec un prompt structuré demandant un audit global. Les deux stratégies coexistent via le champ `slice_strategy` dans `ContractSliceResult` et `consensus_meta`. La comparaison function-level vs full-contract est un axe de benchmark explicite.

### 2.3 — Double taxonomie de sévérité

Le SoTA utilise deux taxonomies concurrentes :

| Taxonomie | Niveaux | Utilisé par |
|:---|:---|:---|
| **Trail of Bits** | High / Medium / Low / Informational (4) | ToB, ConsenSys Diligence |
| **SWC + compétitions** | Critical / High / Medium / Low / Informational (5) | Immunefi, Sherlock, Code4rena |

EPP supporte les deux via un champ `severity_taxonomy` dans le frame :

```python
# Dans le frame smartcontract_audit_v1.0
"severity_taxonomy": "tob_4level",  # ou "swc_5level"
"severity_levels_tob": ["high", "medium", "low", "informational"],
"severity_levels_swc": ["critical", "high", "medium", "low", "informational"],
```

**Choix hackathon** : `tob_4level` par défaut (alignement avec la firme de référence). Le mapping `swc_5level → tob_4level` est trivial : `critical` → `high`. Le choix de taxonomie est documenté dans `consensus_meta.audit_meta.severity_taxonomy`.

### 2.4 — Adaptation des prompts VERIFY pour l'audit

Nouveaux templates dans `cycle_prompts.py` — mode VERIFY/AUDIT :

**ASSESS_AUDIT** : Le modèle reçoit une `ContractUnit` et doit produire :
- Classification par catégorie : SWC Registry (SWC-107, SWC-104, etc.) ET/OU Trail of Bits vulnerability classes (Access Controls, Timing, Undefined Behavior, Data Validation, etc.)
- Verdict par vulnérabilité potentielle : `VULNERABLE` / `SAFE` / `UNCERTAIN`
- Confidence [0,1] et evidence textuelle avec numéros de ligne
- Gravité selon la taxonomie active (`tob_4level` par défaut)

**CHALLENGE_AUDIT** : Rotation circulaire identique au VERIFY standard. Le modèle[i] reçoit le verdict du modèle[(i+1)%N] et doit le contester ou le confirmer avec des arguments de code spécifiques (numéros de ligne, patterns détectés).

**ADJUDICATE_AUDIT** : Synthèse de tous les verdicts. Production d'un vecteur de scores par catégorie, plus un score global de sécurité.

**Extension de `claim_type`** : nouvelle valeur `"security_audit"` dans le majority vote `cycle_manager.py`. Penalty factor dans `CLAIM_TYPE_PENALTIES` : `"security_audit": 1.0` (pas de pénalité — c'est un claim empirique vérifiable).

**Format du prompt ASSESS_AUDIT** :

```
<CONTRACT_CONTEXT>
// Imports and inheritance
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
contract TokenVault is ReentrancyGuard {
  mapping(address => uint256) public balances;
</CONTRACT_CONTEXT>

<FUNCTION_UNDER_AUDIT>
function withdraw(uint256 amount) external {
    require(balances[msg.sender] >= amount, "Insufficient balance");
    (bool success, ) = msg.sender.call{value: amount}("");
    require(success, "Transfer failed");
    balances[msg.sender] -= amount;
}
</FUNCTION_UNDER_AUDIT>

<UNIT_METADATA>
visibility: external | access_level: public | modifiers: none
state_writes: [balances] | external_calls: [msg.sender.call]
</UNIT_METADATA>

Assess this function for security vulnerabilities.
For EACH potential vulnerability found, respond in JSON:
{
  "vulnerabilities": [
    {
      "swc_id": "SWC-107",
      "tob_class": "Undefined Behavior",
      "title": "Reentrancy in withdraw",
      "severity": "high",
      "verdict": "VULNERABLE",
      "confidence": 0.95,
      "evidence": "Line 4: external call before state update (line 5). Classic checks-effects-interactions violation.",
      "affected_lines": [4, 5]
    }
  ],
  "overall_safety": "VULNERABLE",
  "summary": "..."
}
```

### 2.7 — Base de données d'audit isolée : `epp_audit_devnet.db`

Les attestations d'audit sont stockées dans `data/epp_audit_devnet.db`, jamais dans `data/epp_devnet.db`. Les deux bases partagent le même schéma (`schema.sql`) mais sont physiquement séparées.

**Justification** : les attestations d'audit ne doivent pas polluer le graphe de connaissances principal. Les métriques Brier scores, le cache épistémique (ADR-013), et les tier transitions du pipeline principal restent isolés des données d'audit.

**Le benchmark** utilise une troisième DB éphémère (`data/benchmark_audit.db`) créée et détruite à chaque run de benchmark. Cette DB n'est jamais persistée.

### 2.10 — Intégration avec ADR-013 (Cache)

Le cache épistémique s'applique à l'audit dans `epp_audit_devnet.db` : si la même fonction du même contrat (identifié par `contract_hash + unit_id`) a été délibérée dans le TTL, le cache retourne l'attestation existante. Le `contract_hash` change si le code source est modifié → invalidation automatique.

Pour le benchmark, `use_cache=False` est obligatoire (cohérence avec scenario_6).

## 5. Contraintes d'implémentation

### 5.1 — Isolation du module audit

Le répertoire `services/audit/` est un module autonome. Il importe `pipeline.run_pipeline()` et `services/sources/adapters/`, mais **aucun module existant n'importe `services/audit/`**. L'audit est un consommateur du pipeline, pas un composant du pipeline.

Exception unique : `cycle_prompts.py` reçoit les templates d'audit. C'est cohérent avec le pattern existant (EXPLORE + VERIFY templates coexistent déjà dans ce fichier).

### 5.2 — Le slicer est remplaçable

`contract_slicer.py` expose une interface `slice_contract(path, strategy) → ContractSliceResult`. Le `strategy` est un paramètre versionné. Le slicer `function_level_v1` est le premier implémenté. Un futur `full_contract_v2` est un remplacement drop-in.

Le slicer ne doit JAMAIS être appelé depuis le pipeline ESMM. Il est appelé par `audit_runner.py` qui ensuite appelle le pipeline N fois.

### 5.3 — Formatage du prompt

Le code source d'une `ContractUnit` est injecté dans le prompt ASSESS_AUDIT entre balises explicites (`<CONTRACT_CONTEXT>`, `<FUNCTION_UNDER_AUDIT>`, `<UNIT_METADATA>`). Les metadata (visibility, access_level, state_writes, external_calls) sont passées dans une section séparée pour que le modèle puisse les utiliser sans les "inventer".

### 5.4 — Le benchmark ne touche pas les DB de production

`audit_benchmark.py` utilise une DB SQLite éphémère (`data/benchmark_audit.db`), jamais `data/epp_audit_devnet.db` ni `data/epp_devnet.db`. Les attestations de benchmark ne polluent aucun graphe persistant.

### 5.5 — Migration `services/rwa/` → `services/sources/` (procédure)

Ce chantier est un **pré-requis bloquant**. Procédure formelle :

1. **Diagnostic** : Claude Code exécute `grep -rn "services/rwa\|services.rwa\|from.*rwa" --include="*.py" .` et transmet la sortie brute
2. **Validation Opus** : vérification du périmètre, identification des zones à risque (imports circulaires, `__init__.py`, tests)

## 8. Questions ouvertes — COMMUNITY_DECISION_REQUIRED

**Q1 — Agrégation contrat-level.** N fonctions produisent N attestations. **Approche hackathon : pré-indexation structurée semi-automatisée.** Le score global est le score du maillon faible (min severity × min consensus_score). Les N attestations individuelles constituent un index structuré riche — chaque fonction, son verdict, son entropie, sa catégorie SWC/ToB — consultable par un auditeur humain. La machine produit l'index et le signal ; l'humain prononce le verdict final. **Vision long terme :** quand les modèles seront plus matures et les benchmarks auront prouvé la fiabilité des agrégations automatiques, l'index pourra être "essoré" en un verdict agrégé unique. Cette transition sera un axe de benchmark explicite (corrélation index→verdict humain sur N audits).

**Q2 — Attestation on-chain granulaire vs agrégée.** Faut-il ancrer on-chain chaque attestation par fonction, ou seulement l'attestation agrégée du contrat ? Le coût en transactions Solana est linéaire en N. Un compromis : ancrer l'agrégée on-chain, stocker les détails off-chain (SQLite dans `epp_audit_devnet.db`) avec le lien `previous_hash`.

**Q3 — Mise à jour d'audit.** Un contrat audité à T est modifié à T+30j. Le `contract_hash` change → les attestations sont invalidées. Faut-il un mécanisme de diff-audit (auditer uniquement les fonctions modifiées) ? Cela nécessite un module de diff sémantique, pas seulement textuel.

**Q4 — Interaction Slither/ESMM.** Si Slither détecte une vulnérabilité mais l'ESMM la juge `SAFE`, quel tier assigner ? Si l'ESMM détecte mais pas Slither ? **Approche hackathon :** la concordance/discordance est un signal documenté dans `consensus_meta.audit_meta.static_analysis_concordance`, pas une résolution automatique. L'index structuré présente les deux verdicts côte à côte. L'humain tranche. **Vision long terme :** quand suffisamment de données de corrélation seront accumulées (benchmark Phase 2+), un modèle de pondération concordance→tier pourra être calibré empiriquement.

**Q5 — Extension au-delà de la sécurité.** L'audit de gas optimization, de conformité aux standards (ERC-20/721/1155), ou de qualité de code suit le même pattern. Le framework Trail of Bits `code-maturity-assessor` (9 catégories : arithmetic safety, access controls, complexity, MEV risks, etc.) est un blueprint naturel. Frames séparés recommandés (`smartcontract_gas_v1.0`, `smartcontract_erc20_compliance_v1.0`) plutôt que surcharge du frame unique — cohérence avec l'approche "un frame = un domaine de mesure" (ADR-005).
