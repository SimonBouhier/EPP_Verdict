**Date**: 2026-02-15
**Status**: Active
**Dependencies**: ADR-005, ADR-007

## Context
An attestation stores a result (score, signature) but not the methodology that produced it (weighting formula, normalization version, semantic thresholds).
Without this metadata, attestations produced under different strategies (e.g., before/after the addition of semantic merge) are incomparable, and scientific reproducibility is impossible.

## Decision

### Storage
Add a `consensus_meta` column (JSON/TEXT) to the `attestations` table.

### Structure
Three mandatory sections:
1. **`methodology`**: algorithms used (e.g., `hash_exact_v2+semantic_merge_v1`), normalization version, weighting strategy.
2. **`conditions`**: resolved model versions, weights, cycle sequence.
3. **`diagnostics`**: Shannon entropy of votes, semantic dispersion, `ambiguity_detected` flag.

### Integrity
- **Included** in `portable_json` (on-chain payload).
- **Excluded** from the `claim_hash` computation (ADR-006). The hash defines the identity of the claim (*what*); the metadata defines provenance (*how*).

### Migration
Existing attestations receive an explicit migration JSON: `{"methodology": {"consensus_method": "pre-ADR-010"}}`.

## Consequences
- Obligation to populate `consensus_meta` at crystallization.
- Any change to the ESMM strategy must increment `consensus_method`.
- Increase of the on-chain payload size (~2 KB).
